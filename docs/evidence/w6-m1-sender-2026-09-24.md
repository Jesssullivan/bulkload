# 2026-09-24 — W6 M1 PR 1: the negotiated thin-pack sender (R-N60; #48, TIN-4545)

This is the evidence for the first of three W6 M1 PRs (R-N127): negotiation,
segmenting and the sender, as a library that does not depend on the
transport (`crates/bulkload-agent/src/git_carry/carry_v2*`). The
destination's quarantine ingest, ref transaction and journal are PR 2; the
v5 frames are PR 3, after W4's wire PR.

The rulings it is judged against:
- **R-N60:** negotiated thin packs instead of bundles.
- **R-N74 as amended by R-N97:** sent bytes ≤ 1.1× `missing_thin_pack_bytes`,
  and sent objects ≤ the estimate's `missing_objects`.
- **R-N113:** the first round sends exactly the held tips as haves; the
  exactness oracle is upload-pack over exactly that have list.
- **R-N116:** the haves go ancestors first.
- **R-N75:** a partial-clone destination, or a shallow one at a frontier
  other than the source's, is refused `GIT_HAVES_UNPROVABLE`.
- **R-N121:** child stderr is classified, never echoed; with a store it is
  kept privately under a keyed digest.

All work is on fixtures that `crates/bulkload-agent/tests/git_carry_v2.rs`
builds in temp directories and removes. Nothing ran on sting, on an estate
repository or through a product verb (R-N56).

To reproduce, run
`cargo test -p bulkload-agent --test git_carry_v2 -- --nocapture`. Each
measurement prints as an `m1 case=<name> ...` line.

## What the sender does

1. **Offer.** The destination's tips, shallow frontier and partial flag come
   from `git-carry-estimate`'s probe (`Offer::probe`).
2. **First round** (`first_round`). The haves are exactly the offered tips
   the source holds as objects. They are ordered by the position of their
   peeled commit in `rev-list --topo-order --reverse`, ties by oid. Tips
   that peel to no commit (a tag of a tree or blob, a ref at a blob) go
   last, by oid (**spike D1**). The wants are the estimate's: every source
   tip and stash entry, minus the held tips.
3. **Object list** (`PackPlan::build`). `rev-list --objects-edge
   --missing=print` (`--objects-edge-aggressive` for a shallow destination)
   over the wants `--not` the haves, under `pack.useSparse=false`,
   `pack.useBitmaps=false`, `pack.threads=2` and `pack.windowMemory=64m`.
   Any `?<oid>` line refuses (`source_lacks_reachable_objects`); nothing is
   sent for an object the source cannot supply.
4. **Segments.** Objects are assigned to segments of at most the cap
   (`DEFAULT_SEGMENT_CAP`, 64 MiB of `%(objectsize:disk)`) in
   (type, basename, path) order. Each segment then keeps rev-list order, so
   a list that fits one segment is packed exactly as a single list.
5. **List.** The plan persists as `<state>/git-carry-v2/lists/<pack_id>.list`
   (`ListStore`), raw bytes, where `pack_id` is the BLAKE3 of the file. It
   records the wants, the ordered haves, the shallow lines, the cap, the edge
   lines and every segment's object lines. The file is created 0600 with
   `O_EXCL|O_NOFOLLOW`, synced, and linked into place without replacement.
   A state dir inside the source is refused.
6. **Send** (`PackPlan::send_segment`). `pack-objects --stdout
   --delta-base-offset` in list mode, fed the edge lines and the segment's
   object lines. There is no `--thin` (spike Q1 caveat 1) and no
   `--missing`: an object that vanished since the list was made refuses the
   segment. The pack streams into the caller's sink through one reused
   buffer. The receipt records the segment's object count, bytes and BLAKE3,
   with the git build and pins beside them.
7. **Resume.** `ListStore::load(pack_id)` verifies the digest and decodes
   the list; the caller sends segments `k..`. A regenerated segment's BLAKE3
   is never required to match the first attempt's (**spike D6**).

## What the tests assert

On every fixture, `check()` asserts:
- the haves are exactly the destination tips the source holds (checked with
  `cat-file -e`, independently of the product), with no duplicates;
- no have precedes a proper ancestor of itself (`merge-base
  --is-ancestor`), and every non-commit have comes after every commit have;
- each segment's pack header counts exactly its list lines, each segment
  indexes **alone** with `--fix-thin` against the destination's store, and
  the segments are disjoint;
- the union of the segments' object sets **equals** the set upload-pack
  sends for exactly that have list, in that order, with the destination's
  shallow lines (R-N113);
- sent objects ≤ the estimate's `missing_objects`, and equal to its
  `missing_thin_pack_objects`;
- at the default cap, sent bytes ≤ 1.1× `missing_thin_pack_bytes`;
- when there is one segment, it is **byte-identical** to upload-pack's pack;
- the destination ingests every segment and passes `fsck --strict`.

**Random DAGs** (proptest, 12 cases): 2–8 commits with up to two parents
each, random source tips, random held commits (named or not by any source
ref), an optional destination-only tip, and a 512 B or default cap. Every
case passed the full `check()`. The observed ratios were 1.0000 at the
default cap and 1.027–1.044 at 512 B (3–6 segments).

**Resume** (delta fixture, 64 KiB cap, 3 segments): the plan was persisted;
segment 0 was indexed, segment 1 was cut off mid-stream and `index-pack`
refused it. The plan was then read back by `pack_id` and **only segments
1–2 were packed again** (113,901 of 173,422 B, observed). The union passed
the refs-only connectivity check, carried exactly upload-pack's 188 objects,
and passed `fsck --strict`. The regenerated segment 1 happened to be
byte-identical (observed, not asserted: spike D6).

**Refusals** (asserted): a partial-clone destination and a shallow one at a
different frontier (R-N75); an offer tip or want that is not an object name
(`HEAD`, `--all`, `-n1`, a 39-digit prefix); a zero cap; a segment index
past the end; a source that lacks an object the walk reaches (at build); an
object deleted between the list and the pack (at send, `pack_objects_failed`
with a classified stderr and no byte of it in the receipt); a sink that
fails part-way (its own `IO` refusal, and the child ends on its own); a
state dir inside the source, for `Source::probe`, `Offer::probe` and
`ListStore::persist`, including through a symlink.

## Folded from #70

- **DF1:** `StderrStore::open` writes nothing; `stderr/` and the key are
  created by the first capture. A state dir inside a repository stays empty
  and `git status` stays clean (asserted in
  `a_state_dir_inside_a_repository_is_refused`).
- **DF2:** containment compares the device and inode of the state dir and
  every ancestor, recorded while the state dir is opened by descriptor. A
  symlink, a case alias and the `/System/Volumes/Data` firmlink spelling of
  the source are all refused
  (`a_state_dir_inside_a_repository_is_refused_under_any_spelling`). Both
  tests fail on the previous store and pass on this one.

## Open

- **Source shallow, destination full (#55's R4-2).** Negotiation follows the
  estimate: it refuses only a shallow destination whose frontier differs.
  With a shallow source and a full destination, the sender sends commits
  whose parents lie behind the source's frontier; PR 2's connectivity check
  would refuse the publish unless the destination already holds them. This
  needs a ruling (see the agent note).
- The segment cap is 64 MiB of stored size, the plan's D2 figure. A pack
  larger than one segment pays a per-segment cost (1.4 % on the delta
  fixture at 64 KiB). No cohort-1 repository's missing set is near the cap:
  the largest stored size is glorious.build's 9.651 MB
  (`git-carry-estimate-2026-09-23.md`).
