## Q1 — pack-objects list mode with edges

Pipeline tested:
1. Run `rev-list --objects-edge[-aggressive] --missing=allow-any --stdin`
   (wants, then `--not` and the haves).
2. Restrict the result to `rev-list --objects --use-bitmap-index` (see
   below).
3. Feed the result to `pack-objects --stdout --delta-base-offset
   --missing=allow-any`.

Three things are compared: the list-mode pack; the estimate (#55's revs-mode
`pack-objects --thin --revs` with the re-review pins); and the pack a real
`git fetch` receives. The real fetch runs into a copy of the destination with
no `pack.*` pins, and `GIT_TRACE_PACKFILE` captures the received pack verbatim.

To get the object set of a thin pack, it is indexed with `--fix-thin` into a
throwaway quarantine. The set is the `.idx` entries whose offset lies before
the received trailer, because `--fix-thin` appends its bases after the
received objects.

| Fixture | Shape | Walk | Estimate objs / B | Sent objs / B | Fetch objs / B | Sent set = fetch | Bytes = estimate |
|---|---|---|---|---|---|---|---|
| delta-heavy | full | 44 | 44 / 19,031 | 44 / 19,031 | 44 / 19,031 | yes | yes |
| rename-heavy | full | 36 | 36 / 43,917 | 36 / 43,917 | 36 / 43,917 | yes | yes |
| tag-only (tag + tag-of-tag) | full | 2 | 2 / 270 | 2 / 270 | 2 / 270 | yes | yes |
| submodule gitlink | full | 3 | 3 / 348 | 3 / 348 | 3 / 348 | yes | yes |
| matching shallow frontier | shallow | 12 | 12 / 55,994 | 12 / 55,994 | 12 / 55,994 | yes | yes |
| fork below have | full | 8 | 8 / 2,606 | 8 / 2,606 | 8 / 2,606 | yes | yes |
| fork below have | shallow | 8 | 4 / 420 | 4 / 420 | 4 / 420 | yes | yes |
| bitmap source (reverted blob) | full | 4 | 4 / 9,886 | 3 / 290 | 3 / 290 | yes | no (subset) |

- `pack.threads=2` gives the same bytes on every fixture.
- Every list-mode pack was then ingested through the Q3 quarantine and
  published, and `fsck --strict` came back clean. `--fix-thin` appended 4
  bases for delta-heavy and 2 for fork-below-have-full.
- R-N97 gate: sent set = fetch set on 8/8 fixtures. Sent objects ≤ estimate
  objects on 8/8. Sent bytes ≤ 1.1× estimate bytes on 8/8, the largest ratio
  being 1.00.

Caveats. Each one changes the plan:
1. **`--thin` cannot be used in list mode.** In pack-objects, `--thin` turns
   on the internal rev-list, which then reads the `-<oid>` lines as revisions:
   `fatal: not a rev '-<oid>'`. List mode omits `--thin`. The `-<oid>` edge
   lines supply the preferred bases, and the result is still thin.
2. **The edge rule depends on the destination's shape (the re-review pin).**
   A full destination gets `--objects-edge`, and a shallow destination gets
   `--objects-edge-aggressive`, which is what upload-pack's `--shallow`
   selects.
   - In the fork-below-have fixture, the want forks from the have's parent and
     takes the have's tree. The plain rule counts 8 objects; the aggressive
     rule and a real fetch into the shallow destination count 4.
   - #55's estimate without `--shallow` reports 8, the same over-count the
     re-review saw on blahaj (38 against 20).
   - The aggressive rule would also be smaller for a full destination (4
     against 8). But a real fetch into a full destination sends 8, and R-N97
     requires set equality with the fetch, so the full rule stays.
3. **Bitmaps: the sender must intersect with exact reachability.** With
   `pack.useBitmaps=false` the estimate walks the edge closure. In the
   fixture, a blob reverted to a version that only an older have-ancestor
   holds is counted as missing (4 objects).
   - A real fetch from a bitmapped source sends the exact set (3 objects).
   - Without the pin, #55's revs-mode pack also has 3 objects, while its walk
     counts 4. That is the mismatch the re-review found. Measured here, the
     bitmap pack has **fewer** objects than the walk, not more.
   - The sender therefore intersects the edge list with
     `rev-list --objects --use-bitmap-index`, which is the exact set when a
     bitmap exists and the ordinary walk otherwise.
   - With the intersection, the sent set equals the real fetch set and stays
     ≤ the estimate. #55's estimate stays an upper bound, which R-N97 accepts.
4. `pack.useSparse` did not change any set here: every vanilla fetch uses
   Git's default `pack.useSparse=true` and matched the pinned list. #55's
   cohort run is the only evidence of a sparse difference.
5. List lines carry raw paths, so a path containing a newline would break the
   `<pack_id>.list` format. The persisted list needs quoting or length
   prefixes.

## Q2 — segmentation

Fixture: 8 text files × 30 delta rounds, plus 4 incompressible 24 KiB blobs.
The source is repacked, and the destination holds only the base commit. That
gives 188 missing objects and a single thin pack of 171,014 B. The cap is
64 KiB of `%(objectsize:disk)`. Each segment is the edge lines plus its own
object lines, packed in list mode. Each segment was ingested **alone**, into
a fresh quarantine whose only alternate is the destination store.

| Order | Segments | Segmented bytes | Overhead vs one pack | Largest segment | Each alone |
|---|---|---|---|---|---|
| rev-list order | 3 | 207,836 | +21.5 % | 101,656 B | ok |
| (type, path) order | 3 | 173,420 | +1.4 % | 67,286 B | ok |

Resume run in (type, path) order, 3 segments:
- Segments 0..k−1 ingested. Segment k=1 was then cut off mid-stream, and
  `index-pack` refused it with `fatal: early EOF`. It left `tmp_pack_*` in
  the quarantine's `pack/`.
- The refs-only connectivity check refused the incomplete set.
- The leftovers were swept. `<pack_id>.list` was re-read, and **only
  segments 1..2** were regenerated: 113,901 of 173,420 B. With
  `pack.threads=1` they were byte-identical to the first run.
- Result: connectivity ok, then migration, one `create`, the `.keep`s
  dropped, and `fsck --strict` clean.

Caveats that change the plan:
- **Order before cutting.** The list must be ordered by (type, path) so that
  one path's versions share a segment; rev-list order costs +21.5 %.
- **The cap is on estimated stored bytes, not sent bytes.** `objectsize:disk`
  is the source's stored size, and reused deltas get recomputed once their
  base falls in another segment. So segments overshoot the cap: 67,286 B for
  a 65,536 B cap in type-path order, 101,656 B in rev-list order. Either cut
  with headroom, or treat the ~64 MiB target as soft; the wire's ≤ 4 MiB
  `PackData` frames are unaffected.
- **Sweep before resume.** A failed `index-pack` leaves `tmp_pack_*`, so the
  resume path must sweep the quarantine's `pack/` first.
- **Reproducible regeneration (observed).** Regenerated segments were
  byte-identical (2/2 at `pack.threads=1`, same git version). The plan's
  claim that "pack bytes are not reproducible" is too strong for a fixed git
  version and thread count. Integrity should still rest on `index-pack`
  recomputing every oid.

## Q3 — quarantine ingest

Command builder. It keeps `git()`'s strip list and adds `GIT_QUARANTINE_PATH`
to it, so nothing inherited can redirect objects. A typed `Objects` scope then
chooses between:
- `Repository`;
- `Quarantine { dir, main }`, which sets `GIT_OBJECT_DIRECTORY=dir`,
  `GIT_ALTERNATE_OBJECT_DIRECTORIES=main` and `GIT_QUARANTINE_PATH=dir`.

The builder is `git_in()` in the test file and is not wired into any verb.

Sequence:
1. Open `objects/incoming-*`.
2. Run `index-pack --stdin --fix-thin --keep` once per segment.
3. Run `rev-list --objects --stdin --not --all --quiet` over the new tips,
   under the quarantine env.
4. Migrate `.keep`, then `.pack`, `.rev`, and `.idx` last. Fsync `pack/`,
   remove the quarantine, and fsync `objects/`.
5. Publish with one `update-ref --stdin -z` transaction outside the
   quarantine.
6. Drop the `.keep` files.

| Case | Result |
|---|---|
| Have from refs | Connectivity ok. Published, `.keep` dropped, `fsck --strict` clean. |
| **Deleted parent.** The have-query answered yes for unreferenced `x`, and `x`'s parent was then deleted. | Refused at **connectivity** (`error: Could not read <p>` / `fatal: revision walk setup failed`). No ref, no pack migrated, quarantine removed. |
| **Prune after have-query.** `x` was unreferenced and loose, then `prune --expire=now` ran. | Refused at **`index-pack`** (`fatal: pack has 2 unresolved deltas`): thin deltas pointed at pruned bases. No ref, no pack, quarantine removed. |
| `update-ref` under the quarantine env | Git refuses: `fatal: ref updates forbidden inside quarantine environment`. |
| Object missing under an existing ref | The check **passes**, because it trusts refs and `x`'s parent is only reachable from a ref. `fsck` does report it. |

Caveats that change the plan:
- **A stale have can surface at two stages.** It shows up either as
  "segment invalid" (an unresolved thin base at `index-pack`) or as
  "connectivity missing". Both refusal codes are needed, and both must map to
  "have-set stale → re-negotiate".
- **"Trusts only refs" is literal.** A destination whose ref closure is
  already damaged passes the check. That case belongs to R-N75 and to a
  preflight fsck or `cat-file` audit, not to the connectivity check.

## Q4 — ~1,000-parent state commit

Setup: N native tips with one commit and blob each, created with fast-import.
S is built by `commit-tree` over the sorted tips, with a fixed author and
date. The native refs are then deleted, so only the state ref keeps the
history. The pack goes into a fresh bare destination. Timings are from the
serial run under git 2.54.0; the 2.52.0 run is within 2×.

| N | S bytes | Pack B | index-pack | fsck --strict | commit-graph write / verify | gc --prune=now | fsck after gc | reachable | log --graph |
|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 48,169 | 197,065 | 36 ms | ok, 82 ms | ok, 34 ms / ok | ok, 225 ms | ok | 1,001 | 240 ms, 1.0 MB |
| 2,000 | 96,169 | 396,034 | 26 ms | ok, 52 ms | ok, 57 ms / ok | ok, 186 ms | ok | 2,001 | 1,322 ms, 4.0 MB |

Decision: the **one-ref-per-snapshot model stands** and the per-ref fallback
is not needed. The only superlinear cost is `log --graph`: its output grows
roughly with N², and it took 3.9 s / 12.5 s for 1,000 / 2,000 parents under
parallel load. Tooling and receipts should never run `log --graph` over S.

## Q5 — fast-import `M` with an alternates-only oid

Setup: P (`store.git`) has `objects/info/alternates` pointing at a live
store, which holds a blob and a tree P does not. The fast-import stream
contains `M 100644 <blob> worktree/a.txt` and `M 040000 <tree> worktree/dir`.
- The import succeeds, and `cat-file` reads the content through P's ref.
- Neither oid appears in P's pack (`show-index`) or in its loose store.
- `fsck` is clean with the alternate and **fails** without it, which proves
  the object was referenced, not copied.
- An oid in neither store is refused:
  `fatal: blob not found: M 100644 2222… x`.

Caveat that changes the plan: P's refs, `refs/ledger/*` and `state`, pin
objects that live only in the live repository. The live repository's `gc`
cannot see P's refs, so after a branch is deleted and pruned in the live repo,
P's ledger refs dangle. Two options: before P relies on a blob, P must hold it
itself (`repack -a` without `-l`, or write worktree blobs into P); or the
ledger must re-verify presence under `GIT_NO_LAZY_FETCH` and treat an absent
blob as a miss.

## Q6 — byte identity

S is built twice: once from parents `[c3, c1]` and once from
`[c1, c3, c1]`, with the same meta blobs and fixed identity and date. Both
give the same oid and identical `cat-file commit` bytes.
- The destination holds S under `refs/carry/v1/src/item/state`. The
  re-run's list against it is empty, and pack-objects emits a 0-object,
  32-byte pack. The sender should send no pack at all.
- `create` of the existing ref is refused, while `verify` succeeds and leaves
  the ref file's mtime unchanged. So the op must be chosen from the
  destination's ref state: `verify` when equal, `create` when absent.
- A changed meta input gives a new S and a 4-object list.

## Plan assumptions this spike changes

1. D2 "Object list": change `pack-objects --stdout --thin --delta-base-offset`
   to `pack-objects --stdout --delta-base-offset` in list mode, with no
   `--thin`; the `-<oid>` edge lines make it thin.
2. D2 "Object list": the edge rule is `--objects-edge` for a full destination
   and `--objects-edge-aggressive` for a shallow one, matching upload-pack's
   `--shallow` (R-N97, re-review).
3. D2 "Object list": intersect with `rev-list --objects --use-bitmap-index`,
   so that a bitmapped source sends exactly what a real fetch sends (R-N97).
   #55's `missing_thin_pack_bytes` becomes an upper bound, not an equality.
4. Pin `pack.useSparse=false`, `pack.useBitmaps=false` and a fixed
   `pack.threads` in the new command builder.
5. D2 segments:
   - order the list by (type, path) before cutting;
   - the ~64 MiB cap is soft, because the estimate uses stored size;
   - the `<pack_id>.list` format must quote paths;
   - resume must sweep `tmp_pack_*` first.
6. D2 "Pack bytes are not reproducible": they are reproducible at a fixed git
   version and `pack.threads`. Integrity still rests on `index-pack`.
7. D2 ingest: the quarantine builder is a typed scope over the existing strip
   list, and Git itself forbids ref updates inside it. A stale have can fail
   at `index-pack` or at connectivity, so both refusal codes map to
   re-negotiation. The connectivity check does not audit existing ref
   closures, so a preflight audit carries R-N75.
8. D2 ledger: objects referenced through alternates are not owned by P, and
   P must copy or re-verify before trusting them.
9. D2 snapshot model: keep one ref per snapshot. Drop the per-ref fallback
   from the M1 risk list, and add "never run `log --graph` over S".
10. D2 re-run: send no pack for an empty list, and choose `verify` or
    `create` from the destination's ref state.
