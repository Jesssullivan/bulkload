# 2026-09-23 — W6 M1 git-internals spike (R-N93; #48, TIN-4545)

This spike checks the git-internals assumptions listed at the end of the plan's
"D2 Git carry v2" section, under "To confirm in an M1 spike".

The rulings it is judged against:
- **R-N60:** negotiated thin packs.
- **R-N74 as amended by R-N97:** sent bytes ≤ 1.1× `missing_thin_pack_bytes`,
  and sent objects ≤ the estimate.
- **R-N113:** M1 sends exactly the held tips as haves, and the exactness
  oracle is upload-pack over that set.
- **R-N116:** the haves are ordered ancestors first.

  source's, or one that is a partial clone.

## Q1 — list mode against upload-pack (R-N113, R-N116)

**Request.** M1's first round is built as follows:
- **Haves:** exactly the held tips, meaning every destination tip (refs and
  `HEAD`) the source holds, ordered ancestors first. The order is the
  topological order of the peeled commits.
- **Wants:** the fixture's named tips. For B and P1, the wants are every
  source tip the destination does not hold.
- **Shallow:** a shallow destination also sends its `shallow` lines. R-N75
  requires its frontier to equal the source's, and the test asserts that.

**Three packs are compared:**
1. **Sender.** `rev-list --objects-edge --missing=allow-any --stdin` (or
   `--objects-edge-aggressive` for a shallow destination), fed straight into
   `pack-objects --stdout --delta-base-offset --missing=allow-any`. There is
   no trim.
2. **Estimate.** #55's `missing_thin_pack_bytes`: `pack-objects --thin
   --revs`. For a shallow destination it runs as upload-pack runs it:
   `--shallow-file ''`, then `--shallow <oid>` lines, then `--shallow`.
3. **Oracle.** `upload-pack --stateless-rpc` over protocol v2, sent exactly
   those wants, haves (in that order) and shallow lines, under the same pins.
   It is also run with the haves child first, to show why the order matters.

**How a pack's object set is read.** The pack is indexed with `--fix-thin`
into a throwaway quarantine. The set is the `.idx` entries whose offset lies
before the received trailer.

| Fixture | Shape | Held | Walk | Estimate objs / B | Sent objs / B | upload-pack objs / B | Sent = oracle | Child first objs / B |
|---|---|---|---|---|---|---|---|---|
| delta-heavy | full | 1 | 44 | 44 / 19,031 | 44 / 19,031 | 44 / 19,031 | set + bytes | 44 / 19,031 |
| rename-heavy | full | 1 | 36 | 36 / 43,917 | 36 / 43,917 | 36 / 43,917 | set + bytes | 36 / 43,917 |
| tag-only (tag + tag-of-tag) | full | 1 | 2 | 2 / 270 | 2 / 270 | 2 / 270 | set + bytes | 2 / 270 |
| submodule gitlink | full | 1 | 3 | 3 / 348 | 3 / 348 | 3 / 348 | set + bytes | 3 / 348 |
| matching shallow frontier | shallow | 1 | 12 | 12 / 55,994 | 12 / 55,994 | 12 / 55,994 | set + bytes | 12 / 55,994 |
| fork below have | full | 1 | 8 | 8 / 2,606 | 8 / 2,606 | 8 / 2,606 | set + bytes | 8 / 2,606 |
| fork below have | shallow | 1 | 8 | 4 / 420 | 4 / 420 | 4 / 420 | set + bytes | 4 / 420 |
| **B** (#55 R3-1) | full | 2 | 2 | 2 / 298 | 2 / 298 | 2 / 298 | set + bytes | 2 / 298 |
| **P1** seed 1 (R-N116) | shallow | 2 | 3 | 2 / 245 | 2 / 245 | 2 / 245 | set + bytes | **3 / 5,018** |
| **P1** seed 2 | shallow | 2 | 3 | 2 / 245 | 2 / 245 | 2 / 245 | set + bytes | **3 / 5,017** |
| bitmap source | full | 1 | 4 | 4 / 9,886 | 4 / 9,886 | 4 / 9,886 | set + bytes | 4 / 9,886 |
| bitmap source, shallow destination | shallow | 1 | 4 | 4 / 9,886 | 4 / 9,886 | 4 / 9,886 | set + bytes | 4 / 9,886 |

**Gate results:**
- **R-N113 set equality:** 12 of 12 runs.
- **Object bound** (sent ≤ estimate): 12 of 12.
- **Byte gate:** 12 of 12. The largest ratio of sent to estimate bytes is
  1.00.
- **Ingest:** every sent pack was then ingested through the Q3 quarantine
  with the preflight, published, and passed `fsck --strict`. `--fix-thin`
  appended 4 bases for delta-heavy, 2 for fork-below-have-full, and 1 each
  for B and P1.

**The walk is not the gate.** On P1 the walk (`rev-list --objects`) counts 3
objects, but aggressive edges over both held tips send 2. The gate is always
the estimate and the upload-pack oracle, never the raw walk.

The caveats below change the plan.

1. **List mode cannot use `--thin`.** In pack-objects, `--thin` turns on the
   internal rev-list, which then reads the `-<oid>` lines as revisions.
   `q1_list_mode_rejects_thin` asserts the resulting error:
   `fatal: not a rev '-<oid>'`. List mode omits `--thin`. The `-<oid>` edge
   lines supply the preferred bases, so the pack is still thin.
2. **The edge rule depends on the destination's shape.** A full destination
   gets `--objects-edge`; a shallow one gets `--objects-edge-aggressive`,
   which is what upload-pack's `--shallow` selects.
   - In the fork-below-have-shallow fixture, the plain rule counts 8 objects
     and the aggressive rule counts 4.
   - #55's estimate without its shallow form reports 8. That is the same
     over-count the #55 re-review saw on blahaj (38 objects against 20).
3. **Have order matters, ancestors first (R-N116).** Offered child first,
   upload-pack drops a held parent as already implied, stops marking its tree,
   and sends a re-added blob. In P1 that is 3 objects / 5,018 B against
   2 / 245 B. Fixture B (two held tips on a full destination) is
   order-insensitive. A `git fetch` oracle offers the haves newest first, so
   for P1 it is wrong in the R-N116 direction. Revision 1's single-held-tip
   fixtures never exercised the order.
4. **Bitmaps are pinned off, and the sender never trims.** Revision 1's plan
   change 3, the `--use-bitmap-index` trim, is **withdrawn** (review B1).
   - With a bitmapped source, an unpinned pack has 3 objects while the walk
     has 4 (`q1_bitmap_source`). This is why `pack.useBitmaps=false` is
     pinned.
   - Under the pin, the sender, the estimate and the pinned oracle all send
     4.
   - For a shallow destination the trim drops a blob the destination needs.
     `q1_bitmap_source_shallow_destination` measured this:
     `trim_keeps_needed_blob=false`, both on the complete source and on the
     source shallow at the destination's frontier.
   - The reviewer's probe then ingested the trimmed pack, and the
     connectivity check refused it (`missing blob object`) on every retry.
     The untrimmed sender's pack published and was fsck-clean.
5. **List lines are bytes.** `rev-list` truncates an object name at a
   newline, so the newline hazard rev 1 described does not exist. The real
   hazard is a path that is not UTF-8: the spike parses lines as `String`,
   which only works for ASCII fixtures. A product `<pack_id>.list` must
   carry raw bytes.

## Q2 — segmentation

**Fixtures.** Both are measured against a destination holding only the base
commit, with a cap of 64 KiB of `%(objectsize:disk)` (plus 32 KiB for the
rename-lineage fixture):
- **delta:** 8 text files × 30 delta rounds, plus 4 incompressible 24 KiB
  blobs; the source is repacked. 188 objects, one pack of 171,014 B.
- **rename-lineages** (the reviewer's): the same history with the directory
  renamed every third round. 172 objects, one pack of 249,441 B.

**Method.** Each segment is the edge lines plus its own object lines, packed
in list mode. Each segment was ingested **alone**, into a fresh quarantine
whose only alternate is the destination's store.

| Fixture | Cap | rev-list order | (type, path) | (type, basename, path) |
|---|---|---|---|---|
| delta | 64 KiB | +21.5 % | +1.4 % | +1.4 % |
| rename-lineages | 64 KiB | +142.7 % | +164.7 % | **+20.1 %** |
| rename-lineages | 32 KiB | +231.6 % | +253.1 % | **+47.6 %** |

On the rename-lineage fixture, basename order beats both other orders at both
caps; the test asserts this. On the delta fixture every path is unique, so
basename order equals (type, path) order. The reviewer's run, at
`pack.threads=1`, measured +153.5 % for (type, path) and +12.7 % for
(type, basename).

**Resume run** (basename order, 3 segments):
1. Segment 0 ingested. Segment k=1 was then cut off mid-stream, and
   `index-pack` refused it with `fatal: early EOF`. It left `tmp_pack_*` in
   the quarantine's `pack/`; the test asserts this.
2. The refs-only connectivity check refused the incomplete set; asserted.
3. The leftovers were swept, and the test asserts the directory is clean.
4. `<pack_id>.list` was re-read and **only segments 1–2** were regenerated:
   113,901 of 173,420 B, asserted to be less than the total.
5. Connectivity passed, then migration, one `create`, the `.keep`s dropped,
   and `fsck --strict` came back clean.

Regenerated segments were byte-identical to the first run (2 of 2). This is
an observation from a single run at the same git build and `pack.threads=2`,
and it is not asserted.

The caveats below change the plan.

- **Order by (type, basename, path) before cutting (plan change 5).** This
  keeps one file's versions together across directory renames, which is how
  pack-objects' name hash groups them. (type, path) scatters renamed
  lineages.
- **The cap is soft.** It is measured on the source's stored size, and a
  reused delta is recomputed once its base falls in another segment. The
  largest delta-fixture segment was 67,286 B against a 65,536 B cap
  (1,750 B over). In rev-list order the largest was 101,656 B, and on the
  rename fixture 73,408 B.
- **Sweep before resume.** A failed `index-pack` leaves `tmp_pack_*`, so the
  resume path sweeps the quarantine's `pack/` first.

## Q3 — quarantine ingest

**The command builder** strips everything `git()` strips, plus
`GIT_QUARANTINE_PATH`. A typed `Objects` scope then selects one of two modes:
- `Repository`;
- `Quarantine { dir, main }`, which sets `GIT_OBJECT_DIRECTORY=dir`,
  `GIT_ALTERNATE_OBJECT_DIRECTORIES=main` and `GIT_QUARANTINE_PATH=dir`.

It is `git_in()` in the test file and is not wired into any verb.

**The sequence:**
1. The **R-N75 held-tip closure preflight** (mandatory; plan change 7):
   `rev-list --objects --missing=print` over the held tips, under
   `GIT_NO_LAZY_FETCH`. It fails closed on any `?` line or error.
2. Open `objects/incoming-*`.
3. `index-pack --stdin --fix-thin --keep` for each segment.
4. `rev-list --objects --stdin --not --all --quiet` over the new tips, under
   the quarantine environment.
5. Migrate `.keep`, then `.pack` and `.rev`, then `.idx` last. Fsync `pack/`,
   remove the quarantine, and fsync `objects/`.
6. One `update-ref --stdin -z` transaction, run outside the quarantine.
7. Drop the `.keep`s.

| Case | Result |
|---|---|
| The have is the held tip | Preflight ok and connectivity ok. Published, `.keep` dropped, `fsck --strict` clean. |
| **Held-tip closure damaged** (review B3). A blob under the held tip is deleted. | **Without** the preflight: the sender excludes the blob, connectivity trusts the ref, and the new ref is **published with a broken closure** (`fsck` fails). **With** it: refused at the preflight (`held-tip closure incomplete: ["?<oid>"]`). Nothing is indexed, no ref is written, and no quarantine is left behind. |
| **Deleted parent.** A have beyond the held tips (a later `GitHaveQuery` answer; R-N113 keeps it out of M1's first round), whose parent is then deleted. | Refused at **connectivity** (`error: Could not read <p>` / `fatal: revision walk setup failed`). No ref, no pack migrated, quarantine removed. |
| **Prune after the have-query.** The same have, pruned with `prune --expire=now`. | Refused at **`index-pack`** (`fatal: pack has 2 unresolved deltas`). No ref, no pack, quarantine removed. |
| `update-ref` under the quarantine environment | Git refuses: `fatal: ref updates forbidden inside quarantine environment`. |

The caveats below change the plan.

- **The preflight is mandatory (plan change 7).** The connectivity check
  trusts existing refs, and under R-N113 every have is one, so a damaged
  held-tip closure is published unless the preflight runs first. The
  preflight's cost grows with the held-tip history: a full object walk per
  first round.
- **A stale have fails at one of two stages.** It surfaces either as
  "segment invalid" (an unresolved thin base at `index-pack`) or as
  "connectivity missing". Both refusal codes must map to "have-set stale →
  re-negotiate".

## Q4 — ~1,000-parent state commit

**Setup:**
- N native tips are created with fast-import, one commit and one blob each.
- S is built with `commit-tree` over the sorted tips, with a fixed author and
  date.
- The native refs are then deleted, so the state ref alone keeps the history.
- The pack is indexed into a fresh bare destination.
- Separately (review M4), a plain `git fetch` of S goes into a second fresh
  repository, followed by `gc --aggressive`, `fsck` and
  `commit-graph write`/`verify`.

The pass/fail results are asserted.

| N | S bytes | Pack B | index-pack | fsck --strict | commit-graph write / verify | gc --prune=now | fsck after gc | reachable | fetch S | gc --aggressive, then fsck and commit-graph |
|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 48,169 | 197,065 | pass | pass | pass / pass | pass | pass | 1,001 | pass | pass |
| 2,000 | 96,169 | 396,034 | pass | pass | pass / pass | pass | pass | 2,001 | pass | pass |

**Timings are observations, not measurements.** They come from single runs on
a shared host and vary several-fold with load. In revision 2's serial run
(git 2.54.0, load average about 30):

| Step | N = 1,000 | N = 2,000 |
|---|---|---|
| `index-pack` | 24 ms | 40 ms |
| `fsck` | 73 ms | 94 ms |
| commit-graph write | 20 ms | 86 ms |
| `gc` | 132 ms | 191 ms |
| fetch of S | 113 ms | 346 ms |
| `gc --aggressive` | 254 ms | 705 ms |
| `log --graph` | 443 ms | 5,122 ms |

Revision 1's serial run gave the same order of magnitude for every step except
`log --graph`: 240 ms and 1,322 ms. Its parallel run took 3.9 s and 12.5 s.

**The only superlinear cost is `log --graph`.** Its output is 1.0 MB at 1,000
parents and 4.0 MB at 2,000, which is N².

**Decision:** the **one-ref-per-snapshot model stands**, and the per-ref
fallback is not needed. Tooling and receipts must never run `log --graph`
over S.

## Q5 — fast-import `M` with an alternates-only oid

**Setup.** P (`store.git`) has `objects/info/alternates` pointing at a live
store that holds a blob and a tree P does not. The fast-import stream
contains `M 100644 <blob> worktree/a.txt` and `M 040000 <tree> worktree/dir`.

**Results:**
- The import succeeds, and `cat-file` reads the content through P's ref.
- Neither oid is in P's packs or loose store.
- `fsck` is clean with the alternate and **fails** without it, so the objects
  were referenced, not copied.
- An oid in neither store is refused:
  `fatal: blob not found: M 100644 2222… x`.
- Review M5:
  - P's default `gc --prune=now` does **not** copy the objects
    (`p_gc_copies=false`), because it repacks local objects only.
  - `repack -a -d` without `-l` **does** copy them.
  - After that, `fsck` of P with its alternate removed is clean.

**Caveat that changes the plan (plan change 8).** P must **copy
alternates-only objects before its ledger ref is published**, with
`repack -a -d` (no `-l`) or by writing the blobs into P. Otherwise a `gc` in
the live repository, after a branch delete, leaves P's ledger ref dangling.
Re-verifying presence under `GIT_NO_LAZY_FETCH` only *detects* that loss
after the fact; it does not prevent it.

## Q6 — byte identity

**Byte identity of S.** S is built twice, from parents `[c3, c1]` and from
`[c1, c3, c1]`, with the same meta blobs and the fixed identity and date.
Both builds give the same oid (`6586f143…`) and identical `cat-file commit`
bytes. The reviewer's cross-build run confirmed the same oid under nixpkgs
2.52.0, nixpkgs 2.54.0 and Apple 2.54.0.

**The re-run.** The destination holds S under
`refs/carry/v1/src/item/state`:
- The re-run's list against S is empty. pack-objects would emit a 0-object,
  32 B pack, so the sender should send no pack at all.
- `create` of the existing ref is refused. `verify` succeeds and leaves the
  ref file's mtime unchanged. The op is therefore chosen from the
  destination's ref state.
- A changed meta input gives a new S and a list of 4 objects.

## Plan assumptions this spike changes

1. **D2 "Object list": no `--thin` in list mode.**
   `pack-objects --stdout --thin --delta-base-offset` becomes
   `pack-objects --stdout --delta-base-offset` in list mode. The `-<oid>` edge
   lines make the pack thin. `--thin` is refused (tested).
2. **D2 "Object list": the edge rule follows the destination's shape.** Use
   `--objects-edge` for a full destination and `--objects-edge-aggressive`
   for a shallow one, matching upload-pack's `--shallow`.
3. **Withdrawn (review B1).** Revision 1 proposed trimming the list with
   `rev-list --use-bitmap-index`. That conflicts with #55's pins, and for a
   shallow destination it drops a needed blob, so ingest is refused on every
   retry. The sender pins `pack.useBitmaps=false` and never trims.
4. **Pins and negotiation (R-N113, R-N116, #55 bb6efa7).**
   - The sender, the estimate and the oracle all pin `pack.useSparse=false`,
     `pack.useBitmaps=false`, `pack.threads=2` and
     `pack.windowMemory=64m`.
   - M1's first round offers exactly the held tips, ancestors first.
   - The exactness oracle is upload-pack over that request, not
     `git fetch`.
5. **D2 segments.**
   - Order the list by **(type, basename, path)** before cutting: +20.1 %
     against +164.7 % for (type, path) on renamed lineages.
   - The ~64 MiB cap is soft, because it is measured on stored size.
   - `<pack_id>.list` carries raw bytes, since paths need not be UTF-8.
   - Resume sweeps `tmp_pack_*` first.
6. **D2 "Pack bytes are not reproducible".** They are reproducible **only for
   the same git build and `pack.threads`**. Apple git 2.54.0 and nixpkgs git
   2.54.0 produced different bytes for every non-empty pack, up to +5.9 %
   (rename-heavy: 46,487 B against 43,917 B), while the object sets and S's
   oid were identical. Integrity rests on `index-pack` recomputing every oid.
   Receipts must record the git build and the pins beside each segment's
   BLAKE3.
7. **D2 ingest.**
   - The **R-N75 held-tip closure preflight is mandatory**:
     `rev-list --objects --missing=print` over the held tips under
     `GIT_NO_LAZY_FETCH`, failing closed, run before any segment. Without it
     a ref with a broken closure is published (tested).
   - The quarantine builder is a typed scope over the existing strip list,
     and Git itself forbids ref updates inside it.
   - A stale have fails at `index-pack` or at connectivity, and both
     refusals map to re-negotiation.
8. **D2 ledger.** P **copies** alternates-only objects (`repack -a -d`
   without `-l`, or by writing them into P) **before its ledger ref is
   published**. A default `gc` in P does not copy them, and re-verifying only
   detects the loss.
9. **D2 snapshot model.** Keep one ref per snapshot, and drop the per-ref
   fallback from the M1 risk list. Never run `log --graph` over S.
10. **D2 re-run.** Send no pack for an empty list, and choose `verify` or
    `create` from the destination's ref state.
