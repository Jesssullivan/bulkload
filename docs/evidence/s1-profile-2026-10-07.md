# S1 profile: where a native initial copy spends its time (2026-10-07, INFORMATIONAL)

> **Informational only. Not a gate sample.** This file changes no code and
> holds no R23 verdict. It answers OI-1003-Q114: profile first, then bring
> back ranked options.

Rulings: OI-1003-Q114 (profile first), OI-1003-Q107, OI-1003-Q96 (mbp-13,
measurement only), R-N13.

## Why

Two earlier readings disagree with the measurements below.

- The S1 seal breakdown (`s1-seal-breakdown-2026-10-07.md`) gave syncs as a
  share of wall time. It defines that share as summed counter time, an upper
  bound on what removing the syncs could save.
- The gated sample of #210's head (`5b4cbe4`, on #210's branch:
  `docs/evidence/r23-2026-10-07-2146Z-mbp-13-pr210.md`) batched 20 of the 23
  files with two `syncfs` calls. Flush time fell by about 140 ms, but native
  initial wall time did not move: 852 ms, against A at 876 ms and rclone at
  333 ms.

The seals overlap the transfer, so they are not its critical path. This file
looks for what is.

## Rig and method

- **Host.** `mbp-13` (Intel i7-5557U, 4 CPUs, Linux 6.19, xfs). It was idle
  (load below 0.3) before each run.
- **Binary.** `bulkload-bench` built from `5b4cbe4` with
  `CARGO_PROFILE_RELEASE_STRIP=none` and `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`.
  That is the same code generation as the rig's stripped binary, with
  symbols added.
- **Profile.** `perf record -F 1999 -g` (perf 7.1.4 from nixpkgs) of
  `bulkload-bench --only native --reps 3 --informational --priority normal`
  over the sealed corpus v1 (23 files, 239,819,837 bytes). There are five
  native copies: the fixture seed plus the timed initial samples, at 812,
  713 and 685 ms.
  - The sealed corpus is read-only, so the run ended with `EACCES` at the 1 %
    delta. `r23_ab.py` passes a writable private copy; this run did not need
    the delta.
- **Limits.**
  - `perf_event_paranoid=2` allows **user-space samples only**. Kernel time
    (page-cache copies of reads and writes, xfs, scheduler) is invisible
    here.
  - The release build has no frame pointers, so samples are attributed by
    leaf symbol and by thread, not by call stack.
- **rclone.** `/nix/store/v5xbkynmfg8ml23d82m09s802nmj2r6f-rclone-1.74.4`,
  with the bench's flags, timed with `/usr/bin/time` three times and traced
  once with `strace -f -c`.

## Reading

- **Native is not CPU-bound.** In user space a copy costs about 1.1 CPU-seconds
  (capture about 0.55 s, receive about 0.25 s, the rest smaller). rclone
  spends about 0.85 user CPU-seconds, about the same. The difference is
  concurrency:
  - rclone keeps about 2.7 of the 4 CPUs busy for 0.32 s;
  - native keeps about 1.5 busy for about 0.75 s, and no thread is saturated.
- **The workers mostly wait.** `queue_wait_ns` is about 0.8–1.0 s summed over
  four workers, about two thirds of their span. The receive thread is about
  one third busy. The stages hand work to each other more slowly than any of
  them computes. Candidates:
  - the in-process wire between the halves (frame-by-frame handoff);
  - one receive thread doing verify and writes in series;
  - credit or Held turnaround tied to group commits.

  User-space sampling cannot tell these apart; off-CPU (scheduler) tracing
  needs privileges this rig does not grant.
- **The syncs do not set the pace**, as #210's sample showed.
- **Hashing twice is affordable** at this size: the destination verify is
  about 250 ms of one thread, in parallel with capture. Removing it (verify
  once in loopback) would save CPU but not obviously wall time, because no
  stage is CPU-saturated.

## Ranked options (each needs an operator ruling)

1. **Instrument the stage hand-offs (measure first, no behaviour change).**
   Add per-stage blocked-time counters:
   - workers blocked on the send queue;
   - the sender blocked on the wire;
   - the receiver blocked on the wire and on writes;
   - the time from Held to credit.

   One informational rig run then names the stalled stage. Cost: counters
   only. R25 and verify-once are untouched.
2. **Widen the receive side.** Verify and write frames on several threads,
   keeping the commit order. It removes a serial stage if that stage is the
   stall. It is a destination engine change: the data-before-record order and
   P23 / P33 still hold, but it needs a model check.
3. **Loosen the in-process wire.** Use bigger frames or batches, or hand
   buffers off without copying, between the halves of a local `copy`. No
   invariant changes.
4. **Verify once in loopback.** Drop the destination's re-hash when both halves
   share a process. It saves CPU (about 250 ms per copy). Its wall-time gain
   is uncertain while no stage is saturated. It relaxes "every received byte
   is verified exactly once" for loopback only.
