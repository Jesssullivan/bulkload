# Q42 lane L3: large-ref hazard probes, sting, 2026-10-04

**Label: informational, sting, ungated.** These are not gate samples. R-N81
power and load rules do not gate them, but every record carries its load1.

Q42 lane L3 (OI-1003-Q42 to Q45) gathers the sting-side "evidence that
would change it" for the carry_v2 deletion. carry_v2 stays frozen and was
not run (OI-1003-Q15). The neo half is deferred; see
[Pending](#pending-the-neo-read-only-estimate-pass-deferred). The
decision packet these figures answer is
`docs/plans/2026-10-04-git-engine-decision.md` on PR #173: its "Ref count
changes the picture" item, and the large-ref hazard corpus it names as one
way to settle Q45's allowance.

## Findings

1. **At 119,761 carry-shaped refs, v1 refuses the repository on every
   pass.**
   - The capture header is 20,745,391 B, 3,968,175 B over the 16 MiB cap.
   - `git-export` refuses it `GIT_INVENTORY_MALFORMED`, and so does
     `estate-capture`, which then exits `CONTRACT_SELF_INCONSISTENT`. Both
     refusals are typed: no panic and no bare IO. Run B repeated each 3
     times, with the same header and codes.
   - A canonical carry ref costs 135 B + its source slug + its suffix per
     header line, so no carry inventory of 119,761 refs fits.
   - Where the cap falls depends on the real names. The synthetic
     short-slug corpus (3 B slug) reaches it at about 96,855 refs. blahaj's
     real inventory (122,994 refs, mostly a 16 B slug, mean suffix 50.8 B),
     modelled read-only, reaches it at about 84,432 refs; its own header
     would be 24,439,460 B, 7,662,244 B over.
2. **Grouped items have a cap window.** At 96,849 refs, a plan base fits
   (22,259 B under), but its grouped items' rewritten headers do not
   (33,880 B over). The items are captured and recorded, then refused by
   the next pass and by `estate-apply` (run A, one sample).
3. **A changed pass's per-ref CPU is loose-ref filesystem work, not the
   walk.**
   - A chained capture costs **0.51 ms of CPU per ref** (fitted over 5 ref
     counts × 3 samples, r² 0.98; 0.18 ms user, 0.33 ms sys): 58.4 s
     (55.3 to 67.2 s) at 119,761 refs.
   - At 119,761 refs, the reuse fetch of the retained bundle takes 39 to
     47 % of that pass. The one `update-ref --stdin` transaction that writes
     every private ref as a loose file takes 27 to 30 % (82 % of it sys),
     and `bundle verify` about 19 %.
   - The edge-aggressive walk, timed inside the agent's own private
     repository, takes 1.33 to 1.60 s of CPU there: 2.4 to 2.5 % of the
     pass. It lists 4 objects and packs 3,342 B, against the control's
     479,876 B.
   - Run A timed the walk over packed refs (0.13 to 0.25 s), a fast path the
     agent never takes. Its "under 0.5 % of the pass" is withdrawn.
   - In a reftable repository the same refs are written in 1.5 to 1.6 s of
     CPU instead of 14.8 to 17.0 s, and scanned in 0.2 s instead of 1.5 s or
     more. So the per-ref cost belongs to loose refs on this filesystem, not
     to v1 as such.
4. **The inputs to M (SHA-1)**, fitted across corpora that vary refs, seats
   and tree width:
   - c ≈ 1.4 KB;
   - a = 42 B + the exported refname, per ref;
   - p = 54 B per source-held tip;
   - b ≈ 24 B per entry of a changed tree;
   - s ≈ 47 B raw and 5 to 7 B packed per seat: a per-seat term that Q45's
     form lacks.

   At 119,761 compact refs, a·refs is 99.04 % of the 8.85 MB bundle for a
   one-line change.
5. **The neo estimate pass is pending** (see the last section).

## 1. Header bytes against the 16 MiB cap

The agent reads bundle headers in four places, each with the same bounds:
lines of at most 1 MiB, and a refusal once more than 16 MiB (16,777,216 B)
has been consumed. The readers are:

- `git_carry/shared.rs` `prerequisites` (L131 at `8dc26c1`);
- `pack_object_count` (L205);
- `write_with_prerequisites` (L433);
- `git_carry/chain.rs` `advertised`.

| Corpus, verb | Header the agent wrote (B) | Ref lines | Prerequisite lines | Against the cap (B) | Reader verdict |
|---|---:|---:|---:|---:|---|
| `carry-119761`, `git-export` (bundle kept for diagnosis) | 20,745,391 | 119,768 | 0 | +3,968,175 over | `GIT_INVENTORY_MALFORMED` (header over 16 MiB) |
| `carry-119761`, `estate-capture` (private capture kept) | 20,745,391 | 119,768 | 0 | +3,968,175 over | `GIT_INVENTORY_MALFORMED` |
| `compact-119761`, `estate-capture` pass 1 (self-contained) | 8,761,559 | 119,768 | 0 | 8,015,657 under | ok |
| `compact-119761`, `estate-capture` pass 2 (chained) | 8,817,287 | 119,768 | 1,032 | 7,959,929 under | ok |
| `small-compact`, pass 2 (chained) | 22,352 | 263 | 64 | 16,754,864 under | ok |
| `carry-window`, plan base (shared) | 16,754,957 | 96,850 | 0 | 22,259 under | ok |
| `carry-window`, grouped item (main checkout), recorded | 16,811,096 | 96,856 | 1,032 | +33,880 over | `GIT_INVENTORY_MALFORMED` (header over 16 MiB) |

Run B's 3 samples of each `carry-119761` and `compact-119761` row wrote
the same headers. The `carry-window` rows are run A's.

The model and the agent agree. The modelled ref term plus 17 B of signature
and blank line, plus the 7 capture metadata ref lines (487 B), gives each
header the agent wrote, to the byte.

**At 119,761 refs, a carry-shaped inventory cannot fit under the cap,
whatever its native names are.** A canonical carry ref's line is
40 + 1 + 27 (`refs/carry-export/union/v1/`) + slug + 1 + 64 + 1
+ suffix + 1 = **135 B + slug + suffix** (SHA-1). The synthetic corpora's
3 B slug makes that 138 B + suffix; blahaj's slugs are 3 to 16 B. At
119,761 refs the ref term alone fits only if the mean slug plus suffix is
at most 5.09 B (16,777,216 ÷ 119,761 = 140.09). A namespace's own metadata
suffixes (`head`, `staged`, `worktree`, `filesystem-v1`) average 7.75 B, and
its native copies' suffixes start with `refs/`, so every such inventory is
over the cap.

Where the cap falls depends on the real slugs and suffixes:

- **The synthetic short-slug corpus** (slug 3 B, generated suffixes of mean
  35.7 B, at least 4 B): a 173.2 B line, so the cap is reached at **about
  96,855 refs**.
- **blahaj's real inventory** (110,160 of its canonical refs carry the
  16 B slug `neo-20260922-c2a`; mean suffix 50.8 B; 3,233 refs outside the
  carry namespace): a 198.7 B mean line, so the cap is reached at **about
  84,432 refs**. At its 122,994 refs the modelled header is 24,439,460 B,
  7,662,244 B over, against 3.97 MB over for the synthetic corpus.

The packet's estimate, "a header line of about 85 B ... about 10 MB per
changed capture per item", is too low for a carry inventory. The union
prefix, the source slug and the 64-hex snapshot digest add 75 B + the slug
to every line (78 to 91 B for blahaj's slugs), over a plain ref with the
same name. At 119,761 refs, v1 does not pay 10 MB per capture. It
**refuses the repository on every pass**: see section 3. A SHA-256
repository adds 24 B per line, so the synthetic shape's cap comes about
12 % sooner (about 85,068 refs).

For a plain inventory (`refs/carry-export/<name>`, 60 B + the name), the cap
sits at 167,772 refs for a 40 B mean name, and at 229,339 refs for the
compact corpus's 13 B names.

**Which reader trips where.** Every capture passes through
`pack_object_count` (L205) on the bundle it has just written, before any
record is kept. So a self-contained capture, a chained capture and a plan
base are all refused there, as soon as their own header is over the cap.
The other three readers are reached as follows:

- **`chain::advertised`** reads only a prior that this agent already
  accepted at L205. By construction, it cannot see an over-cap header that
  this binary wrote.
- **`write_with_prerequisites` (L433)** caps the header that *git* wrote.
  For a grouped item, git omits every ref whose tip is excluded, so that
  header is small. The header the agent then writes in its place has 54 B
  per base commit, plus every private ref, and it is **not** measured at
  write time: the stats come from git's bundle.
- **`prerequisites` (L131)** then meets that header on the next pass
  (`retained_capture`'s `requires_base`, `chainable`) and at apply
  (`import_base`). The cap-window probe in section 3 measures this
  write/read asymmetry.

These slopes add up to the pass's 0.51 ms per ref. Three things carry it:

- **Loose-ref creation.** `capture_refs` writes every private ref in one
  `update-ref --stdin -z` transaction. Git 2.52's files backend writes each
  one as a loose file, and nothing in the agent packs them: the one
  `pack-refs` outside carry_v2 is a test (`estate.rs` L3393). The
  transaction takes 16.6 to 18.1 s at 119,761 refs, 82 % of it sys.
- **The reuse fetch.** It reads the whole retained bundle (S3 finding 5),
  here 9.57 MB, of which 8.76 MB is header, to fetch two refs. 55 to 64 %
  of its CPU is sys. How it splits between parsing the header and ref work
  in the loose private repository was not measured.
- **`bundle verify`** reads back the bundle the pass has just written,
  header and all.

At 119,761 refs, 62 to 66 % of a chained pass's CPU is sys (36.3 of
58.4 s at the median), and so is 0.33 of its 0.51 ms per ref.

### The edge-aggressive walk

`write_excluding_tip_trees` runs `rev-list --objects-edge-aggressive --all
--stdin` with one `^tip` line per source-held tip of the prior.

**Inside the agent.** Run B's child attribution times that child in the
agent's own private repository:

- 1.33, 1.48 and 1.60 s of CPU at 119,761 refs: 2.4 to 2.5 % of each pass;
- 1.26, 5.08 and 2.57 s at 90,000 refs: 2.9 to 10.2 %.

**Replayed.** The probe also replays the walk in a private-like bare
repository:

- its alternates name the source's objects;
- it holds every source ref under the export mapping, plus `head`;
- it adds one new parentless worktree commit, which is HEAD's tree with one
  changed blob two levels down;
- the exclusions are every distinct tip, peeled to a commit the source
  holds, as `chain::source_held_tips` builds them.

Run B builds that repository three ways:

- **loose**, the agent's storage: one `update-ref --stdin -z` transaction
  and nothing after it;
- **packed**, the same and then `pack-refs --all`, as run A did;
- **reftable**, with `--ref-format=reftable`.

**The cap refuses as a typed value. No run panicked (exit 101 or "panicked
at"), and none refused with a bare `IO` or `FRAME_CODEC`.** The
`carry-119761` rows hold in all of run B's 3 samples. Three caveats for S4
dispositions:

- **The code names the wrong cause.** The inventory is well formed. It is
  only large. An operator reading `GIT_INVENTORY_MALFORMED` would look for
  corruption. A size-specific code, or a reason on the existing one, would
  route the disposition correctly.
- **A refused pass leaves its write behind.** It writes the whole bundle
  (21.6 MB here) before L205 reads it back and refuses. The private capture
  is kept for diagnosis (as `export_repository` documents), and
  `write_source_pack_bytes` stays 0 for it, because `PackStats::record`
  refuses before it counts. Every pass over such a repository repeats this
  cost: 24.0 to 32.8 s of CPU per refused `git-export` and 31.4 to 33.6 s
  per refused `estate-capture` in run B, mostly the ref-creating
  transaction and `bundle`.
- **It recurs on every pass.** Nothing changes between passes, so the item
  is refused every time until its header fits: below about 96,855 refs for
  the synthetic short-slug shape, or about 84,432 at blahaj's real mean
  line.

**The cap window: a grouped item is written over the cap, and refused
only afterwards.** At 96,849 carry-shaped refs (run A):

- **The plan base passes.** Its header is 16,754,957 B, 22,259 B under the
  cap.
- **Each grouped item goes over.** Its bundle declares the base's 1,032
  commits as prerequisites (55,728 B) on top of the same inventory: a
  header of 16,811,096 B, 33,880 B over.
- **Pass 1 records both items.** `write_with_prerequisites` caps only
  git's own header, which is small because git omits excluded tips, and it
  takes its stats from git's bundle. So both items are captured and
  recorded, and the verb exits 0. `write_source_pack_bytes` (18,619,065 B)
  counts git's bundles, not the rewritten ones.
- **Later readers refuse both.** The unchanged next pass refuses both at
  `requires_base` (`retained_capture`), and `estate-apply` refuses both at
  `import_base`.

Every refusal is typed, but each comes after the capture was accepted as
custody, and no later verb accepts that custody. The window exists
wherever a grouped repository's base header lies within its prerequisite
and metadata bytes of the cap: here, a base header of about 16,720,000 to
16,777,216 B.

A write-side check would refuse at capture, where the disposition belongs.
The check is to measure the final header against the same cap before the
rename, as `write_excluding_tip_trees` gets through `PackStats::record`.
This window is a property of `8dc26c1`: #177 has since moved grouped
items onto that path (see "What this changes").

## 4. The inputs to Q45's byte allowance M

`q42_probes.py summarize` splits each chained capture bundle into terms.
The header terms are measured line by line:

- a·refs is the ref lines whose names map from a source ref;
- the metadata ref lines are the other 7: `head`, `head-symbolic`,
  `staged`, `worktree`, `configuration-v1`, `exclude` and `filesystem-v1`,
  under `refs/carry-export/`;
- p·tips is the prerequisite lines.

The pack terms are in-pack sizes by object role, from `verify-pack -v`
after `bundle unbundle` into a scratch repository that reads the source's
objects.

**What `check` = 0 does and does not show.** In all 22 of run B's chained
bundles, the terms add up to the bundle (`check` = 0). That holds for any
well-formed bundle, whatever the split: a bundle is its header + 32 B + the
in-pack sizes. So `check`, `pack_check` and `header_check` (all 0) confirm
the parse, not the terms. The terms rest on two other things:

- **a·refs is measured, not modelled.** In every bundle the measured
  source-ref lines equal the corpus model to the byte (`a_model_delta`
  = 0), and their count equals the source's refs (`a_lines_delta` = 0).
  Run A's split took a·refs from the model and left the metadata lines as
  the residual; `summarize` marks it `a_source: modelled`.
- **The units are fitted across corpora**, not taken from one: refs 256 to
  119,761, seats 1,040 to 16,640, and changed-tree entries 80 to 320.

**Why s varies in the pack.** The filesystem-v1 rows are 46.7 to 47.1 B
per seat raw at every seat count, and none was stored as a delta (0 of
22). Their packed size is zlib's, and each row carries its seat's inode and
mtime. A corpus packs to the same size in each of its samples. Across the
4,160-seat corpora, though, it runs from 5.21 to 5.95 B per seat, and it
tracks how many distinct mtimes the checkout holds (354 to 542; Pearson r
0.86 over 6 corpora). Run A's `small-compact` packed at 7.12 B per seat (its
stat values were not recorded). So s in the pack depends on how and when
the checkout's files were written, not only on how many there are. The raw
47 B is the stable unit; 5 to 7 B is the observed packed range.

Pass 2's input was one appended line in one tracked file, two levels
down. Its wire cost, as a share of the bundle:

- **compact-119761: 99.04 % header refs, 0.63 % prerequisites, 0.28 % seat
  rows**, and 103 B of content;
- **small-compact: 38.2 % refs, 45.0 % seat rows**.

**Evidence that would change Q45's form, M = c + a·refs + b·trees:**

1. **A per-seat term is missing.** filesystem-v1 holds every carried seat's
   row, so every changed capture rewrites it whole: about 47 B raw and 5 to
   7 B packed per seat. At 4,160 seats, that is 21 to 30 KB: the largest
   term of a small-ref capture, and most of S3's 28 to 40 KB "capture
   metadata" residual. So M needs an s·seats term, or filesystem-v1 needs a
   delta form.
2. **A per-tip term is missing.** A chained capture declares one 54 B
   prerequisite line per source-held distinct tip of its prior; a grouped
   item, one per base commit. That is 55.7 KB at the corpora's 1,032 tips;
   blahaj's real inventory has 2,378 distinct tip commits, so up to
   128,412 B. It scales with distinct tips, not refs.
3. **b is per entry, not per tree.** A changed tree is packed whole (about
   24 B per entry), so b·trees should be b·Σ(entries of changed trees).
4. **a·refs is bounded by the cap.** Past about 84,432 refs at blahaj's
   real mean line (about 96,855 for the synthetic short-slug shape, about
   167,772 plain refs at 40 B names) a·refs is not a cost but a refusal. M
   is only meaningful under the cap. Above it, the item needs a typed
   disposition (S4) or a v1 change, such as excluding the carry namespaces
   from the header or capturing them by digest.
5. **CPU scales with refs too: about 0.51 ms per ref per changed capture**
   (0.31 ms on a first pass), mostly loose-ref filesystem work on this
   host. A byte allowance does not bound it; S2's +2.0 load1 budget is the
   relevant bound.

With those terms, the measured inputs are:

    M ≈ 1.4 KB + (42 B + refname)·refs + 54 B·tips + 24 B·Σentries(changed trees) + 5–7 B·seats (packed; 47 B raw)   (SHA-1)

## What this changes in the Q15 packet's list

- **"Ref count changes the picture": yes, more sharply than the packet
  estimated.**
  - At 119,761 carry-shaped refs, v1 does not cost about 10 MB per
    changed capture. It refuses the repository, typed, on every pass.
  - Below the cap, the header is about 99 % of a one-line change's bundle,
    and a chained pass costs about 0.51 ms of CPU per ref: 58 s at 119,761
    refs on sting, 62 to 66 % of it sys.
  - v2 negotiates refs instead of listing them in every capture, so this
    is a measured case for v2 or hybrid negotiation of the ref layer.
  - Two v1 alternatives remain: a header change (carry namespaces by
    digest) for the bytes, and a reftable private repository for the
    per-ref CPU.
- **The edge-aggressive walk is not a reason to keep v2.** Inside the
  agent at 119,761 refs it costs 1.3 to 1.6 s of CPU, 2.4 to 2.5 % of a 55
  to 67 s chained pass (5.1 s, 10.2 %, in one 90,000-ref sample). Its cost
  is a scan of the loose refs, which the non-aggressive control pays too.
  It is what keeps chained v1 bundles small: 3,342 B against 479,876 B
  here.
- **Two v1 defects to add to the follow-up list, both at large ref counts.**
  - A grouped item's final header is not checked against the cap at write.
    It is recorded, then refused by every later reader (section 3).
  - `prerequisite_commits` spawns two git children per base head: about
    0.79 ks of CPU projected at 96,850 heads × 2 items.
  - Follow-up 1 rewrites that same group-base path, so both fit there.
  - **Since run B, follow-up 1 has merged** (#177, 2026-10-05 03:12Z). At
    origin/main `b8521c2`, `write_with_prerequisites` is gone: a grouped
    item is written by `write_excluding_tip_trees`, which ends in
    `PackStats::record` and so reads its own header under the cap. By
    reading the code, the first defect no longer applies there; it was
    not re-probed. `prerequisite_commits` still spawns two children per
    base head at `b8521c2`.
- **The ref term is unrelated to follow-ups 1 to 4.** Follow-up 1
  (group-base tip-tree exclusion) and follow-up 2 (grouped chaining) leave
  a·refs and p·tips untouched. Follow-up 4 (reuse without the whole
  retained bundle) would remove the 9.57 MB re-read here, the largest
  child of a chained pass.

## Limits

- The corpora are synthetic and short-slug. The ref shape follows #48's
  blahaj counts: 119,761 refs over 1,032 distinct oids, in 157 namespaces
  of about 750 native refs, with generated names (one 3 B slug, mean suffix
  35.7 B) and no annotated tags. blahaj's real inventory was modelled
  read-only (section "Corpora") but not run through the agent: its header
  figures are the model's, which matched the agent to the byte on the
  synthetic corpora. The cap conclusion at 119,761 refs holds for any
  slug and suffix (section 1).
- The per-ref slopes are fitted on compact names only. Carry-shaped names
  ran only at 119,761 refs, where they are refused, and at 96,849 refs in
  run A's single grouped pass.
- The walk was replayed only on 64 × 64 trees. Its aggressive cost grows
  with the distinct trees under the excluded tips, and a tree of tens of
  thousands of files was not probed.
- One chained step was measured. Chain depth, re-base and grouped chaining
  are the S3 harness's (#173) and the neo pass's.
- The cap-window grouped pass ran once (run A). Its 1,432 s of CPU, and the
  792 s projected for `prerequisite_commits`, rest on that one sample.
- **No sample was taken in a quiet window.** Run B reports medians and
  spreads of 3 samples, and its slopes fit 15 samples each, but sys-heavy
  CPU inflates under contention. The absolute CPU figures may be biased
  upward by tens of percent: run A's single `compact-119761` pass 1 was
  24 % above run B's median. Wall times are informational only.
- **sting's filesystem.** `/srv/scratch` is xfs over LVM. Loose-ref
  creation and scans are metadata-bound and will cost differently on
  neo's APFS, so no CPU figure here transfers to neo.
- `git-carry-estimate` (the v2 projection) was not run on these corpora.
  Its ref handling is negotiation, not a header, and the neo pass below
  runs it on real repositories.

```bash
# below runs without it.
: "${PLAN:?set PLAN to the neo estate plan the operator names}"
"$A" estate-show "$PLAN" > "$S/plan.txt"
# estate-show prints one Rust Debug line per item:
#   Item { source: "<neo path>", repository: "<sting path>", workspace: ... }
# `repository` is the item's destination on sting. pairs.tsv holds
# SOURCE<TAB>DEST. Debug escapes a quote or backslash in a path; such an
# item is listed in unparsed-items.txt for review, never guessed.
awk -F'"' '$1 == "Item { source: " && $3 == ", repository: " && $2 !~ /\\/ && $4 !~ /\\/ {
             print $2 "\t" $4; next }
           /^Item / { print > "/dev/stderr" }' \
  "$S/plan.txt" > "$S/pairs.tsv" 2> "$S/out/unparsed-items.txt"
cut -f1 "$S/pairs.tsv" > "$S/repos.txt"
while read -r r; do g -C "$r" rev-parse --path-format=absolute --git-common-dir; done \
  < "$S/repos.txt" | sort -u > "$S/commons.txt"
g init --quiet --bare --template= "$S/empty.git"   # an empty destination
```

Samples are taken at t0, at t1 = t0 + 24 h and at t2 = t0 + 7 d. Each one
starts with `sample tN`, which records the host, load1, power and UTC time.

### Metric 1: rewrite+gc fallback frequency

A chained v1 capture excludes only the retained capture's tips that the
source still holds. If a rebase or force-push moves a tip and a gc or prune
then drops the old one, the next capture falls back toward re-packing.

```bash
# t0: every tip of every common repository, and every object they reach.
sample t0
while read -r c; do
  k=$(key "$c")
  g --git-dir="$c" for-each-ref --format='%(objectname) %(refname)' > "$S/out/tips-t0-$k"
  g --git-dir="$c" rev-list --objects --all | cut -d' ' -f1 | sort -u > "$S/out/objects-t0-$k"
done < "$S/commons.txt"

# Hourly for 7 days, the gc indicator: the pack listing v1's custody path
# compares. The loop takes 168 samples and then ends by itself.
cat > "$S/hourly.sh" <<'EOF'
#!/bin/sh
S="$1"; n=0
while [ "$n" -lt 168 ]; do
  while read -r c; do
    k=$(printf %s "$c" | shasum -a 256 | cut -c1-16)
    printf '%s %s\n' "$(date -u +%FT%TZ)" \
      "$(ls -li "$c/objects/pack" | shasum -a 256 | cut -c1-64)" >> "$S/out/packs-$k.log"
  done < "$S/commons.txt"
  n=$((n + 1)); sleep 3600
done
EOF
chmod 700 "$S/hourly.sh"; nohup "$S/hourly.sh" "$S" > "$S/out/hourly.out" 2>&1 &

# t1 (N=1) and t2 (N=2), against the t0 tips.
N=1; sample "t$N"
while read -r c; do
  k=$(key "$c")
  g --git-dir="$c" for-each-ref --format='%(objectname) %(refname)' > "$S/out/tips-t$N-$k"
  # moved: a t0 ref that now names another oid, or is GONE.
  sort -k2 "$S/out/tips-t0-$k" > "$S/out/a-$k"; sort -k2 "$S/out/tips-t$N-$k" > "$S/out/b-$k"
  join -1 2 -2 2 -a 1 -e GONE -o 0,1.1,2.1 "$S/out/a-$k" "$S/out/b-$k" \
    | awk '$2 != $3' > "$S/out/moved-t$N-$k"
  # rewritten: moved, not gone, and OLD is not an ancestor of NEW.
  while read -r ref old new; do
    [ "$new" = GONE ] && continue
    g --git-dir="$c" merge-base --is-ancestor "$old" "$new" 2>/dev/null || echo "$ref $old $new"
  done < "$S/out/moved-t$N-$k" > "$S/out/rewritten-t$N-$k"
  # dropped: a t0 tip the store no longer holds as a commit.
  cut -d' ' -f1 "$S/out/tips-t0-$k" | sort -u | sed 's/$/^{commit}/' \
    | g --git-dir="$c" cat-file --batch-check='%(objectname) %(objecttype)' \
    | awk '$2 == "missing" {sub(/\^\{commit\}$/, "", $1); print $1}' > "$S/out/dropped-t$N-$k"
  # Fallback bytes, for a repository with a dropped tip: a chained capture
  # excludes only the held t0 tips (fed over stdin, deduplicated), so every
  # object it lists that already existed at t0 is re-packed.
  if [ -s "$S/out/dropped-t$N-$k" ]; then
    cut -d' ' -f1 "$S/out/tips-t0-$k" | sort -u | sed 's/$/^{commit}/' \
      | g --git-dir="$c" cat-file --batch-check='%(objectname) %(objecttype)' \
      | awk '$2 == "commit" {print "^" $1}' \
      | g --git-dir="$c" rev-list --objects --all --stdin | cut -d' ' -f1 | sort -u \
      | comm -12 - "$S/out/objects-t0-$k" \
      | g --git-dir="$c" cat-file --batch-check='%(objectsize:disk)' \
      | awk '{s += $1} END {print s + 0}' > "$S/out/fallback-bytes-t$N-$k"
  fi
done < "$S/commons.txt"
```

Report the following:

- rewritten tips, dropped tips and fallback events (repositories with a
  dropped tip) per repository per day;
- fallback bytes per event;
- pack-listing changes per repository per day.

`objects-t0-*` lists every object a repository reaches at t0, about 41 B
per object; a repository of a few million objects needs a few hundred MB.

### Metric 2: chained-item history size

Until Q15 follow-up 3, a chained item re-bases every ninth changed capture
(`CHAIN_DEPTH_LIMIT` 8), at a cost of its history ÷ 9 per changed capture.

```bash
sample metric2
while IFS="$(printf '\t')" read -r r d; do
  {
    printf 'item=%s dest=sting:%s\n' "$r" "$d"
    "$A" git-carry-estimate --state-dir "$S/state" "$r" "$S/empty.git"   # full history
    "$A" git-carry-estimate --state-dir "$S/state" "$r" "sting:$d"       # the v2 delta
    printf 'refs=%s\n' "$(g -C "$r" for-each-ref | wc -l)"                # a-term input
    printf 'seats=%s\n' "$(g -C "$r" ls-files -z | tr -cd '\0' | wc -c)"  # s-term input
  } > "$S/out/history-$(key "$r").txt" 2>&1
done < "$S/pairs.tsv"
```

The sting destination is the plan item's `repository`, reached as
`sting:<path>` (`ssh -T -oBatchMode=yes`). An item whose destination does
not exist on sting yet prints `refused=CODE` for that pair; its v2 delta is
then the full-history figure.

Report these per item:

- `missing_thin_pack_bytes` against the empty destination: the history a
  re-base packs;
- the re-base price, that figure ÷ 9;
- `missing_thin_pack_bytes` against sting: the v2 delta;
- refs and seats;
- the change rate: the share of samples in which HEAD, any ref or the dirty
  set moved.

### Metric 3: grouped growth

Until follow-up 2, a grouped item (several planned worktrees of one common
repository) re-packs all history since its first pass on every changed
capture, once per item. Until follow-up 1, it also re-packs every tracked
blob, because the group base has no tip-tree exclusion.

```bash
sample metric3
while read -r c; do
  printf '%s worktrees=%s\n' "$(key "$c")" \
    "$(g --git-dir="$c" worktree list --porcelain | grep -c '^worktree ')"
done < "$S/commons.txt" > "$S/out/worktrees.txt"
# Tracked blob bytes per planned worktree (the follow-up 1 term):
while read -r r; do
  printf '%s %s\n' "$(key "$r")" "$(g -C "$r" ls-tree -r --format='%(objectname)' HEAD \
    | g -C "$r" cat-file --batch-check='%(objectsize:disk)' | awk '{s += $1} END {print s + 0}')"
done < "$S/repos.txt" > "$S/out/tracked-blob-bytes.txt"
# History since t0 per common repository (the follow-up 2 term), at t1 (N=1)
# and t2 (N=2). The t0 tips go over stdin, deduplicated: as arguments,
# 119,761 of them would pass Darwin's 1 MiB ARG_MAX. A dropped t0 tip cannot
# be excluded (--ignore-missing), so its history counts here too.
N=1
while read -r c; do
  k=$(key "$c")
  printf '%s %s\n' "$k" "$(cut -d' ' -f1 "$S/out/tips-t0-$k" | sort -u | sed 's/^/^/' \
    | g --git-dir="$c" rev-list --objects --all --stdin --ignore-missing | cut -d' ' -f1 \
    | g --git-dir="$c" cat-file --batch-check='%(objectsize:disk)' \
    | awk '{s += $1} END {print s + 0}')"
done < "$S/commons.txt" > "$S/out/history-since-t0-t$N.txt"
```

Grouped growth at t1 or t2 is the sum over groups of planned items × history
since t0. It is reported next to the group base size.

### Metric 4: persistent dirty share

v2 has no snapshot layer, so a worktree that stays dirty across syncs is
state that only v1 (or a hybrid) carries.

```bash
N=0   # 0, 1 or 2: the sample t0, t1 or t2
sample "status-t$N"
while read -r r; do
  g -C "$r" status --porcelain=v2 -z --untracked-files=all > "$S/out/status-$(key "$r")-t$N"
done < "$S/repos.txt"
# dirty: any entry. Dirty bytes: the sizes of the listed worktree paths (stat).
```

Report the following:

- the persistent dirty share: items dirty at t0, t1 and t2, out of all items;
- the dirty byte share: dirty bytes out of tracked bytes, per sample.
