single-file floor is below the rclone median, by 398.982 ms (28.4 %).
Today's native path takes 8559 ms, 6.1× the rclone-as-shipped median.

Notes that bound the verdict:

- **n = 3, with run-order drift.** Every arm here has three samples, and the
  arms ran in fixed blocks, not interleaved. The rclone-as-shipped samples
  fall monotonically across the three repetitions (2095.8, 1404.5,
  1107.6 ms). The floor variants ran as fixed blocks (none, fsync, barrier,
  full), and the `F_FULLFSYNC` block ran last. The medians carry that
  drift. The W3 script interleaves every arm in a rotating order.
- **The single-file floor is not the shape of the corpus.** It writes one
  242.6 MB file, flushes it once, and flushes no directory. It also repeats
  one 8 MiB random block and does not read the source. A mover must write
  23 files, flush each, and flush their directories, which is the
  per-file cost estimated above.
- **Media durability is unproven.** This benchmark does not prove that
  `F_FULLFSYNC` reaches stable media on this USB enclosure (media name
  `RAID`). It shows only what the call costs.
- The floor with `F_BARRIERFSYNC` in place of `F_FULLFSYNC` is 675.437 ms.
  On this USB volume the `pwrite` phase runs at 199.5–387.9 MB/s: the kernel
  throttles the writer once dirty pages build up. The single flush that
  follows cost 38.2–74.2 ms in the durable runs (and up to 96.3 ms at
  256 MiB in the flush runs), whatever its kind (see "Flush cost").
- rclone as shipped writes no data bytes. It clones every file
  (`isCloned: true` 23 times) and then spends its time on MD5 verification of
  both sides (see "rclone clone audit"). Its time is metadata plus hashing,
  not a durable write. The comparison against the floor is still the one
  R-N62 asks for.
- The in-bench rclone arm, which clones from the native fixture on the same
  volume, had an initial median of 2279.156 ms (2 samples). The standalone
  three-rep median above is the stricter (faster) rclone number, so the table
  uses it.
- Power source was not logged for these samples, so it is unknown per
  sample. The W3 script logs it on every row, and R-N81 requires AC power.
- Host contention: other lanes were compiling on neo during this session.
  The 1-minute load average ranged from 3.8 to 21.6 and is recorded on every
  log. The native bench began at load 15.75. The native number is an upper
  bound on today's cost, not a clean baseline.

Reading: on the USB volume, writes above about 16 MiB are throttled to
device speed during `pwrite`. For 64 MiB, 151 ms is 444 MB/s, and 256 MiB
takes 710–1192 ms. The flush that follows then costs 39.0–96.3 ms for
16–256 MiB of dirty data, whatever its kind. Each sample is one file and
one flush, with no directory flush. The written data repeats one 8 MiB
random block. `F_FULLFSYNC` costs about the same as `F_BARRIERFSYNC` and `fsync`
there. On the internal disk, `F_FULLFSYNC` costs 53–85 ms from 64 MiB up,
against 4–10 ms for `fsync` and `F_BARRIERFSYNC`, so full flushes are the
cost that matters on internal storage.

## CPU micro-benchmarks (micro a, b, d)

`bulkload-bench micro {cdc,blake3,socket}`. The input is 256 MiB of
xorshift bytes, which are incompressible like the git packs (socket: 1 GiB).
Each item runs on the P class (`QOS_CLASS_USER_INTERACTIVE`) and on the E
class (`QOS_CLASS_BACKGROUND`). Each class runs one thread, then one thread
per core of the class (2 P, 4 E). Run 1 has 3 reps
(`logs/micro-*.log`, 16:44Z, load1 ≈ 4). Run 3 has 5 reps
(`logs/micro-*-v2.log`, 17:04Z, load1 15.8–22.2) and adds GB/s per
thread-CPU-second (`clock_gettime(CLOCK_THREAD_CPUTIME_ID)`), which does not

Reading, with its limits stated:

- **Core class is not measured cleanly.** Under this contention the P-class
  and E-class per-thread CPU rates are equal within noise. Examples: slice-cut
  1.455 vs 1.508 GB/s, BLAKE3-64K 1.172 vs 1.197 GB/s. `BACKGROUND` confines
  a thread to E-cores. `USER_INTERACTIVE` only prefers P-cores. With the P
  cores saturated by other lanes' builds, the "P" rows most likely ran on
  E-cores. These rows are therefore an E-core-class floor, not a P-core
  number. A clean P-core number needs a quiet host.
  `logs/cpu-quiet.sh` waits for load1 < 2.5 and reruns these items. It had
  not found a quiet window when this document was written.
- Per thread, on the cores actually received: FastCDC slice cutting runs at
  about 1.4–1.5 GB/s. StreamCDC as used today runs at about 1.0 GB/s, so the
  streaming wrapper costs about 30 %. Single-call BLAKE3 runs at about
  1.1–1.2 GB/s per thread at every chunk size tested. Today's copy hashes
  7.93 × P with BLAKE3, which is about 1.6 CPU-seconds of BLAKE3 alone at
  this rate: more than the entire 1.40 s rclone budget. A CPU budget that
  fits needs about 2 passes (CDC plus one BLAKE3 per chunk) spread across
  cores.
- `AF_UNIX` socketpair: the default Darwin buffers are 8 KiB
  (`net.local.stream.sendspace=8192`), which limits throughput to
  0.26–0.71 GB/s. With 4 MiB `SO_SNDBUF`/`SO_RCVBUF` it reaches 8.6–13.3 GB/s
  in the P class, a 23.0×–33.5× speedup (run 1: 13.341 / 0.580; run 3:
  8.583 / 0.256). The local `copy` path uses a default-buffer socketpair
  today.
- **zstd was not micro-benched.** The compression cost item is deferred to
  W5.
- The quiet-window rerun (`logs/cpu-quiet.sh`) never found load1 < 2.5 and
  ran anyway at 18:17Z at load1 18–22 (`logs/micro-*-quiet.log`). It is
  excluded here: it does not meet R-N81 (AC power and load1 < 2.5).

## Link calibration: neo → sting

`head -c 268435456 /dev/urandom | ssh sting 'cat > /dev/null'`. The bytes
were discarded on sting, and nothing was written there. The route is
`utun4` (tailnet). The 4-stream rows start four such pipelines at once and
time until all finish. Log: `logs/link-calibration.log`.

Today one stream runs at about 28 MB/s, and four parallel streams add
nothing (about 26 MB/s aggregate). During the 4-stream run,
`io.tailscale.ipn` used 78–96 % of one core (`top`). The tailnet data path on
neo, not ssh, is the likely ceiling. At 28 MB/s the corpus needs ≥ 8.6 s on
this link for any mover. These rates are 4× the 6.7 MB/s recorded earlier
in #44, so link rate varies from session to session and must be measured
beside every cross-host sample.

## What was not done

- The corpus-shaped durable floor: the mode and the interleaved script are
  in this PR, but the gated measurement belongs to W3 (R-N87, R-N81).
- zstd micro-benchmarks: deferred to W5.
- A clean P-core measurement: the CPU rows ran on a contended host, and the
  "P" rows most likely ran on E-cores (see the CPU section).
- The 4-stream link rows do not record per-stream ssh exit statuses.
- No cross-host `pull` was run: `serve` writes its source state store on the
  source host, and this lane may not write on sting. `pull`/`serve` counters
  were exercised locally through an ssh stand-in instead.
- Bench header volume/device/link fields and a bench `link-calibration` arm
  (listed in #44 contents) are not in this PR. This PR records them in this
  document instead.
