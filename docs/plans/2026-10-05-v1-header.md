# v1 ref table: carrying a full ref set without listing it in the header (OI-1003-Q54), 2026-10-05

Rulings: OI-1003-Q54 (v1 must carry refs-heavy repositories before carry_v2
is deleted), OI-1003-Q42, Q44, Q45, R-N13. Issue #178; evidence
`docs/evidence/2026-10-04-q42-probes.md`.

## The problem

A v1 capture bundle's header lists every carried ref: one
`<oid> refs/carry-export/<name>` line per ref, 135 B + slug + suffix for a
canonical carry ref. The readers cap a header at 16 MiB, so the cap falls
at about 96,855 synthetic carry refs and 84,432 at blahaj's real mean line.
blahaj (122,994 refs) models to a 24.4 MB header and is refused
`GIT_INVENTORY_MALFORMED` on every pass. Below the cap, about 60 % of a
chained pass's per-ref CPU is the reuse fetch and `bundle verify` reading
that header back, and about a third is writing one loose private ref per
carried ref.

## Design: a ref table plus one tip ref per distinct object

The capture's private repository no longer holds one ref per carried ref.
`capture_refs` computes the same `refs/carry-export/...` map as before and
writes:

- **`refs/carry-ref-table/v1`**: a parentless archival commit (fixed
  signature, written by one `fast-import` into the write store) whose tree
  holds the map, content-addressed. It is also the format's marker, named
  outside `refs/carry-export/` so that older readers refuse it (below):
  - `native`: sorted `<oid> <name>\n` lines for every ref outside a
    canonical carry namespace, `name` relative to `refs/carry-export/`
    (`refs/...` and `stashes/<oid>`);
  - `union/<slug>/<digest>/carry-namespace-refs`: one blob per canonical
    namespace `refs/carry/v1/<slug>/<digest>/`, sorted `<oid> <suffix>\n`.
    A namespace is immutable by construction (its digest names its
    content), so its blob is too; the 157 near-identical snapshot blobs of
    a blahaj-shaped inventory share a path suffix and delta against each
    other in the pack.
- **`refs/carry-export/ref-tip-v1/<oid>`**: one ref per distinct target
  object of the map, so `--all` packs exactly what the old refs reached.
- The capture metadata refs (`head`, `head-symbolic`, `staged`, `worktree`,
  `filesystem-v1`, ...) are unchanged and stay in the header.

**Header bound, per distinct object.** A self-contained header is 111 B
per distinct target object (SHA-1; 159 B SHA-256) + about 1.6 KB of
metadata. A thin bundle (a chained link, a plan base's item) adds a
`-<oid> shared base` line per prerequisite, 54 B (78 B SHA-256), and its
prerequisites are about its distinct commit tips: 165 B per distinct
object (237 B SHA-256). The header depends on the distinct objects D, not
on the ref count N, and the gain over the old format (135 to 150 B per
ref) depends on N / D:

- D much smaller than N (blahaj's 122,994 refs over 2,382 distinct
  targets, about 266 KB; the synthetic 119,761-ref corpus over 1,032, about
  115 KB): the header is two orders of magnitude smaller.
- D close to N (one commit per ref: a mirror with `refs/pull/*/head`,
  Gerrit `refs/changes/*`): about 1.3x smaller, and the private repository
  still writes about N tip refs. REFS-SCALE's distinct-heavy rows
  (`tests/refs_scale_distinct.rs`) run this end.

The cap (16 MiB) falls at about 151,100 distinct objects self-contained
(105,500 SHA-256) and at about 101,680 in a thin bundle (70,790 SHA-256). A
thin header over the cap is written self-contained instead (below); only a
self-contained header over the cap is a typed refusal.

**Apply.** `import_verified` takes the bundle's objects with `git bundle
unbundle` (no ref is written), proves every advertised object's closure is
present with one `rev-list --objects` walk (what `fetch`'s connectivity
check gave), reads the table, and rebuilds the old format's header lines
exactly. A destination that already holds every closure takes nothing, as
`fetch` did. Everything after is unchanged: the same native-snapshot
digest, the same `refs/carry/v1/<source>/<digest>/...` names, one
compare-and-create transaction. The import is linear in the bundle: no ref
name is matched against the advertised list (next section).

## Compatibility with retained captures

The reader dispatches on the `refs/carry-ref-table/v1` header ref. A
retained capture without it (every capture written before this change)
takes the old path unchanged; its key, record and sidecars are untouched,
so it stays a hit.
A table without its tips, a tip that names another object, a tip the table
does not use, a table entry with no tip, a header ref that is neither
metadata, table nor tip, or unsorted or duplicate lines all refuse
`GIT_INVENTORY_MALFORMED`. Chains may mix formats: every link is fetched
whole by `chain::flatten`, which re-bundles the head's own refs.

Old-format imports of more than a few tens of thousands of refs passed
every ref name to one `git fetch` argv: the old binary refuses a
119,761-ref capture `IO` (E2BIG). Git matches each exact refspec by a scan
of every advertised ref, so `fetch` with one exact refspec per ref, or per
distinct object, costs O(D x advertised): quadratic when D is close to N
(sting, git 2.52: 56 s, 232 s and 1,001 s of CPU at 10k, 20k and 40k
tips). The import names no ref: `bundle unbundle` plus one connectivity
walk is linear (debug build, `git-import` CPU with its git children: 17.4
to 21.2 s at 32,768 distinct commits, 61.1 s at 110,000; REFS-SCALE's
distinct-heavy rows bound it per distinct object).

**Older readers refuse the new format; no mixed-version apply.** Every
reader before the table (main `818926a`: `import_verified`,
`shallow::unpack`, a plan base's `prerequisite_commits`) refuses a header
name outside `refs/carry-export/` `GIT_INVENTORY_MALFORMED`, before it
fetches or writes anything. With the table ref under that prefix, such a
reader imported a new capture's `ref-tip-v1/<oid>` refs as if they were the
source's and reported success, with none of the source's names. The table
ref is therefore named outside the prefix. A capture written in this format
is applied only by a build that reads it; a pre-change build (on the
destination, or pinned to restore a retained corpus later) refuses it. The
frozen pre-table rule is a test (`refs_scale_tests`), and the old binary
itself refused a new capture on sting (lane note).

## R25 and S3

- **R25.** The table is built from the inventory the snapshot already read;
  no source byte is read for it. The reuse fetch still reads the whole
  retained bundle (`read_source_capture_reuse_bytes`), now with a header
  bounded by distinct targets.
- **S3.** An unchanged estate is a hit as before. A changed capture's
  `a·refs` header term becomes `111 B·D` in the header (`165 B·D` for a
  chained link) plus the table in the pack, compressed and deltaed; the
  table is rewritten whole on every changed capture, like `filesystem-v1`.
  Measured at 119,761 refs over 1,032 distinct objects: about 11 B per
  carried ref in the pack (lane note). The private repository writes D
  refs, not one per carried ref; with D close to N that is still about N.
  Apply still writes every carried ref: that is the restore.

## Restore exactness

- **Refs**: the table is `capture_refs`' map, so the rebuilt header lines
  equal the old ones byte for byte; REFS-SCALE checks the imported set.
- **Symrefs**: carried as today, as plain refs at their resolved value; the
  symbolic HEAD is the `head-symbolic` metadata blob, unchanged.
- **Peeled tags**: an annotated tag ref carries the tag object; the tip ref
  names it, so the tag and its target travel; `^{}` peels identically.
- **HEAD** and **worktree refs**: `head`/`head-symbolic` are unchanged;
  per-worktree refs the captured checkout lists are inventory lines like any
  other.

## L1 thin bundles and chain/base custody (GitCarry.tla)

- The private repository holds the same set of distinct ref tips, so
  `rev-list --objects-edge-aggressive --all` marks the same trees: P64's
  `T(B)` is unchanged, and the only new packed objects are the table's
  commit, trees and blobs, which no prerequisite reaches.
- `chain::source_held_tips` reads the prior's header. Its distinct values
  are the same tips plus the table commit, which no source holds, so the
  prerequisites are unchanged.
- A chained link or a plan base's item whose thin header would be over the
  cap is written self-contained (`chained == false`): refusing would strand
  the item, since every later pass is offered the same prerequisites (the
  chain never grows to its depth reset; a plan base never changes). Apply
  already reads a self-contained bundle without its base or chain.
- `prerequisite_commits` (plan base) skips the base's table ref, whose
  commit lives only in the base's pack, and peels every head in one
  `cat-file --batch-check` instead of two children per head.
- `GitCarry.tla` abstracts header and pack content; names, sidecars,
  records and apply order do not change, so the model needs no change.

## The cap: typed, and checked at write

- New refusal `GIT_INVENTORY_OVER_CAP`: an inventory that is well formed
  but over a carry size bound. The 16 MiB header cap at every reader
  (`prerequisites`, `skip_header`, `chain::advertised`) and every writer,
  the 256 MiB ref-table bound, and the 16 MiB shallow manifest.
- Writers check before they write: `write_full` sums the header from the
  private refs before `bundle create`; `write_excluding_tip_trees` (plan
  base items and chained links) measures the header it built before any
  pack byte, and writes self-contained when it would be over; the shallow
  envelope measures its manifest. No capture is recorded that a later
  reader refuses for size.

## Open (operator)

- **Persisted format.** Every new capture is written in this format; old
  ones still restore. Ratify, or rule a threshold (old format below N refs).
  Ratifying includes the no-mixed-version rule: a destination, and any
  build pinned to restore a retained corpus, runs a build that reads the
  table; an older one refuses the capture `GIT_INVENTORY_MALFORMED`.
- **O(1) header.** Anchoring commit tips under octopus anchor commits would
  bound the header for all-distinct inventories (Gerrit-style), lifting the
  151,100 (101,680 thin) distinct-object cap, but `source_held_tips` would
  then need the prior's pack, not its header.
- **Reftable private repository** (about 30 % of the remaining per-ref CPU
  at apply) is independent and not taken here.
- **Smaller table.** Snapshot namespaces differ in their object names, so
  their blobs delta poorly; naming objects by index into the tip list would
  cut the table's pack bytes further, at the cost of self-describing blobs.
