## 1. Lever 1: verify once in loopback

**What it does.** In a local `copy`, the destination no longer hashes the
chunks its in-process source already hashed. Across processes and hosts
nothing changes: the destination hashes every received byte.

**The capability** (`crates/bulkload-agent/src/transfer/handoff.rs`):

- `SourceChunk { digest, data: Arc<Vec<u8>> }` has private fields and two
  constructors, `hashed` (BLAKE3 of the bytes, counted as
  `blake3_capture_chunk_bytes`) and `checked` (hash, then keep only if equal
  to a manifest digest). Every chunk the source sends is one: a capture's
  (`capture_file`, `chunk_slot`), a retained one (the same value, its digest
  checked against the manifest's), or one read again for `NeedChunks`
  (`checked`). So a chunk always carries the digest of its own bytes, and
  the `Arc` lets nothing write them afterwards.
- `handoff::pair()` makes the joined `HandOut` and `HandIn`. It is private
  to the transfer module and called once, in `copy_with`, where both halves
  run in one process from one build over a socket pair `copy` makes.
  `serve`, `receive` and `receive_with` (so `pull`) take no hand and make
  none, and neither half can be serialised: nothing that arrives over a
  pipe, a socket or `ssh` can stand for one.
- `Payload::vouched(digest)` is true only for a handed chunk whose own
  digest is its frame's. `Inbound::data` then dispatches the job with
  `verify: false` (and `Streaming::accept` stages without hashing). A
  `Payload::Wire` is never vouched for. The size bound stays (`read_wire`
  refuses a handed frame over `MAX_DATA_PAYLOAD`).

**Counters.** New `wire_handed_bytes`: payload bytes taken by hand-off. The
destination's `blake3_dest_wire_verify_bytes` counts every other received
byte, so every received byte is in exactly one of the two
(`tests/w3_engine.rs` asserts the sum; it asserted
`blake3_dest_wire_verify_bytes == bytes_received` before).

**Proofs.**

- Mutation (`src/transfer/tests/levers.rs`,
  `a_cross_host_session_verifies_every_byte_and_its_mutation_is_caught`):
  the public `serve` and `receive` over a socket pair, as `pull` runs them,
  with the third data frame corrupted on the way. The destination refuses
  the file `DIGEST_MISMATCH` and publishes nothing. Under the test-only
  mutation `TRUST_WIRE` (transport bytes taken as vouched for: a verify-once
  applied off the loopback) the same run publishes the corrupt file, and the
  same property check fails. The proof has teeth.
- Mutation on a delta (review round, section 9:
  `a_cross_host_delta_verifies_every_requested_chunk_and_its_mutation_is_caught`):
  a first `serve`/`receive` session, the middle of the file changed, then a
  second session whose first data frame (an answer to `NeedChunks`, the
  manifest-fill path) is corrupted: refused `DIGEST_MISMATCH`, the previous
  output kept; under `TRUST_WIRE` the corrupt delta lands. The scratch
  mutation `verify: false` on the Filling job, which every test passed
  before, now fails this test and the cross-process delta test below.
- Cross-process (`tests/loopback_handoff.rs`): the real
  `bulkload-agent serve` in a child process, `transfer::receive` in the
  test, a relay between them. Clean: `blake3_dest_wire_verify_bytes ==
  bytes_received == payload`, `wire_handed_bytes == 0`; a cross-process
  delta (`a_cross_process_delta_verifies_every_requested_byte`) hashes every
  requested byte the same way. One byte flipped in
  one data frame between the processes: that file is refused
  `DIGEST_MISMATCH`, the others arrive whole.
- Local (`tests/loopback_handoff.rs`): a `copy` hands every byte over
  (`wire_handed_bytes == payload`), hashes none on the destination, and the
  same copy with the hand-off off hashes every byte on both sides.
- Equivalence (`levers.rs`,
  `the_hand_off_and_the_plain_protocol_carry_the_same_tree`): first copy
  and a delta (manifest, local fill, requested chunks from the retained
  capture) give the same trees and the same `completed`, `reused`,
  `bytes_received`, `source_bytes_read` and refusals either way.
- `only_a_handed_chunk_of_the_frames_digest_is_vouched_for`: the rule
  itself.

**Crash checker and R25 argument.** Verify-once removes one CPU step and no
durable step. The destination writes the same bytes at the same offsets,
`End` still waits for every write (`settle_entry`), the group still seals
before its FULL commit, and `Held` still follows that commit. No record
order, seal or commit moved, so the R-N88 power-loss proofs and the
fault harness check the same traces (results in section 5). Bytes the
destination reads back are still hashed: crash adoption of an unrowed
output (#169, `verify_existing`, `blake3_verify_existing_bytes`) and local
reuse (`read_verified`, `blake3_dest_local_reuse_bytes`). The residual it
accepts: a fault that changes memory between the source's hash and the
destination's write in one process goes unseen, where before the
destination's second hash would have caught it. The same window existed
before between the destination's own hash and its `pwrite`.

**TLA.** No row. `BulkloadTransfer.tla` abstracts content as version
numbers and a digest check as equality of versions ("ABSTRACTIONS": "a
digest check is equality of versions"); it has no separate wire-verify
step, so the model's verify did not change. `DirectoryRecords.tla` and
`SqliteCarry.tla` do not model the wire.

## 2. Lever 2: the loosened in-process wire

All of it is loopback-only, behind the same capability, and
`BULKLOAD_LOOPBACK_HANDOFF=0` turns it off with lever 1 (an A/B knob that
only ever adds verification).

- **Direct buffer hand-off.** The source moves each chunk's allocation into
  the hand-off queue, then writes only its 64-byte data header on the
  socket under tag `0xB1` (`TAG_HANDED`, outside v6's 0x01 to 0x03). The
  frame keeps a data frame's place among the control frames, so stream
  order, credit, and every index, offset, size and manifest check are as
  before. The destination takes the chunk when it reads the frame
  (`read_wire`, `HandIn::take`): the queue holds it already, since it was
  handed before its frame was written. Chunks in the queue are within the
  credit window. Wire bytes on the socket fall from about the payload to
  about 1 % of it (69 bytes per 64 KiB average chunk).
- **Batched frames (bigger batches).** The source's frames are written
  through a 64 KiB buffer (`Corked`) and flushed when the sending thread is
  about to wait for its next event (`send_entries`: `try_recv`, then
  `uncork` before a blocking `recv`), when the buffer fills, and before it
  returns. The sending thread waits on nothing but its events, so every
  frame the destination could wait for is on the socket before the source
  waits: no new deadlock. Over a transport (`Plain`) every frame is still
  flushed as it is written.
- **Buffered reads.** Both halves read the socket through a 64 KiB
  `BufReader` (the source's reader thread and the destination's frame loop).
- **Not built** (in scope but not worth it): corking the destination's own
  frames (it writes about 240 credit returns and two frames per entry), a
  larger credit return, frames of several chunks. With the payload off the
  socket, a frame's size no longer matters.

**Wire v6 compatibility for cross-host.** `PROTO_VERSION` (6), `WIRE_SCHEMA`
and `wire_id` are untouched (the proto crate is not changed; its pinned
`wire_id` test still passes). `serve` writes only v6 frames: the
cross-process test decodes every frame the child `serve` writes with
`bulkload_proto::Frame::decode` and sees only tags 0x01 to 0x03. A handed
frame is no v6 frame: the proto codec and the public `read_frame` refuse it
`FRAME_CODEC` (`tests/loopback_handoff.rs`), and so does any `receive`
without the hand-off, which ends the session
(`levers.rs::a_receiver_without_the_hand_off_refuses_a_handed_frame`).

## 3. Lever 3: fewer synced commits

**3a. Stores created directly in WAL mode** (`io/durable.rs`
`wal_database_template`, `init_wal_database`, `interrupted_wal_init`;
`transfer_store.rs` `Store::open`, `finish_wal_init`).

- Before: `configure_sqlite`'s `PRAGMA journal_mode=WAL` on the new empty
  file ran a version-change commit in rollback-journal mode: a `-journal`
  synced twice and the database once per store (the 2026-10-08 trace: 3 per
  store, 6 per copy).
- Now: `Store::open` writes page 1 of an empty WAL-mode database into the
  file it just created with `O_EXCL`, and syncs it, before `SQLite` opens
  it. `SQLite` then finds the header in WAL mode, opens the WAL, and writes
  nothing to the main file before a checkpoint. No `-journal` is made. The
  store's creation commit (schema, authority, markers) is its first write,
  in the WAL, `synchronous=FULL` as before, and the root seal still
  precedes it (#161).
- The template is `SQLite`'s own page: `the_wal_template_is_sqlites_own_first_page`
  compares it with the page `SQLite` 3.51.2 (bundled) writes, and checks a
  database made from it takes a schema, passes `integrity_check`, and is
  never written in its main file before a checkpoint.
  `a_new_store_is_created_directly_in_wal_mode` shows a fresh store's main
  file is the template, unchanged (a version-change commit would have moved
  its change counter), with no `-journal`, and that it reopens with its
  authority.
- Ordering: the page reaches stable media no later than the store's first
  WAL frame. A WAL needs that: `SQLite` deletes the WAL of a database file
  that reads as empty. The seal (review round, section 9) is an `fsync` on
  Linux, the call each replaced `SQLite` sync was, and `F_BARRIERFSYNC` on
  Darwin, where `SQLite`'s replaced syncs were plain `fsync`s (`fullfsync`
  is set only after the switch) and an `F_FULLFSYNC` would add a
  device-cache flush per store. The barrier orders the page ahead of the
  WAL; the root seal (a full flush) and the first commit (`F_FULLFSYNC`)
  drain the device after it.
  It is the precondition `SQLite`'s own journal commit gave before (its
  database sync), so `BulkloadTransfer.tla`'s assumption ("each store's
  state root and database file exist durably once the store's first commit
  returns") and the R-N88 store proofs
  (`every_power_loss_state_of_a_store_open_keeps_the_store` and its teeth,
  which model the database as an opaque file and assert the open writes
  nothing they model) hold as before. The page write and its sync are the
  database file's own I/O, outside the trace and the flush counters, like
  the `SQLite` syncs they replace (on Darwin the barrier is untraced,
  `io::sys::barrier_untraced`).
- Crash inside the page write: the file holds at most one page of zeros and
  template bytes, with no `-wal` (the WAL comes later). `SQLite` would
  refuse a torn header for good, so the next `Store::open` recognises that
  shape (`interrupted_wal_init`) and writes the page again. It never touches
  a file with a `-wal` beside it (a store, possibly open in this process:
  closing a second descriptor would drop its `fcntl` locks), a longer file,
  or any other content. Test:
  `a_store_file_left_inside_its_template_write_is_made_whole` (empty,
  short, all-zero, torn) and a foreign header left alone and refused.
- Saving: 2 of 3 syncs per store on Linux, the rig's platform (mbp-13 runs
  Linux 6.19; the study measured about 1.5 to 3 ms per store there, both
  stores open in parallel). On Darwin, 3 plain `fsync`s become 1
  `F_BARRIERFSYNC`; not measured.
- A/B knob (review round): `BULKLOAD_STORE_WAL_TEMPLATE=0` restores
  `SQLite`'s own switch; the counter `store_wal_templates` counts stores made
  from the template (2 per fresh copy, 0 with the knob off), so a rig sample
  shows its arm. Test: `the_wal_template_knob_turns_lever_3a_off`.
- A store file beside a live `-wal` is never touched:
  `a_store_file_beside_a_wal_is_never_rewritten` (short, zeros, torn main
  file beside the creation commit's WAL; the bytes are unchanged after
  `Store::open`). The scratch mutation that drops the `-wal` guard fails it.

**3b. Fewer destination group commits** (`transfer.rs`
`publication_committer`, `DEST_GROUP_IDLE`, `DEST_GROUP_AGE`,
`DEST_GROUP_IDLE_ENV`; `io/durable.rs` `Limits::group_age`).

- Before: a destination group closed after 20 ms with no new output
  (`GROUP_IDLE`), so a local copy of corpus v1 ran 10 to 18 groups on the
  rig, each a
  `syncfs`, renames, `syncfs` and a FULL commit (the study's largest lever:
  each extra serial group cost 14 to 27 ms on the rig).
- Now: the destination's groups wait 250 ms for the next output and close
  at most 1 s after their first output (`group_age`, new). The stream's
  drain (`Inbound::settle_held`) still closes the last group at once, and
  the file and byte bounds are unchanged. The source ledger's committer
  keeps its 20 ms (its commits are relaxed rows, WP0(g)).
  `BULKLOAD_DEST_GROUP_IDLE_MS` sets the idle for A/B (`20` is before).
- R25 and WP0(g), against the model:
  - `BulkloadTransfer.tla` `Commit` is `\E G \in SUBSET Seats : G # {} /\
    \A s \in G : Ready(s)`: any nonempty set of ready seats commits as one
    group. A larger group is a behaviour every config already explores, and
    the ordering rules stand: `HeldAfterCommit` (`MC_neg_held_before_commit`
    fails without it), `RecordImpliesBytes` (`MC_neg_commit_before_fsync`,
    `MC_neg_commit_before_dirseal`), the strict R25 reading with crashes
    (`MC_r25_strict_main`, `MC_r25_unrowed_bytes`), the relaxed ledger
    (`MC_wp0g`) and the FULL authority it may not relax
    (`MC_wp0g_authority`, `MC_store_root_unsealed`). The spec is
    unchanged, so these rows check the same state spaces (rerun, section
    5). Those rows have at most two seats; the review round added
    `MC_r25_strict_three` for groups of three (above, and section 9).
  - What changes is when outputs become durable, never the order: a larger
    group holds `Held` back longer, and a crash can leave more outputs
    durable with no row. The bound on that is still one group, within the
    same file and byte limits as before, and #169's adoption takes those
    outputs on resume from their capture records with 0 source bytes read
    (`MC_r25_unrowed_bytes`, the `resume-power-loss` proofs).
  - No commit is relaxed. Output groups and directory records stay FULL
    (`Held` follows a FULL commit, R-N102); WP0(g) relaxes only the source
    ledger's rows, which it already did by default. The only "relax"
    WP0(g) allows is therefore already in place.
- Side effect: the space preflight releases an entry's reservation at its
  `Held`. With larger groups, reservations of written but uncommitted
  entries accumulate until their group commits, and a re-probe of free space
  counts those bytes twice. On a nearly full destination this can refuse
  `DESTINATION_SPACE_INSUFFICIENT` earlier than before, by at most a
  group's bytes. It is conservative, never a data loss.
- Expected on the rig, not measured there: once or twice (sting's
  informational census, section 5.2: 1 destination group commit against 3
  to 5). The code and design.md say so as an expectation; the rig series
  replaces it with numbers.
- Model coverage (review round): `MC_r25_strict_three` checks three seats,
  so groups of one, two and three commit, with a crash between two runs
  and the strict R25 reading; an ad hoc action property shows a 3-seat
  group commit is reachable at that bound. The close rules (idle, age,
  files, bytes, drain) are timing: `Commit` takes any nonempty set of ready
  seats at any step, so each rule picks one of the model's choices. The
  power-loss copy is checked at every destination group size of its tree
  (1 to 7 files, `BULKLOAD_FAULT_GROUP_DESTINATION`, section 9).
- Proof: `io::durable::tests::a_group_waits_out_its_idle_and_closes_at_its_age`
  (items 60 ms apart share a group under a long idle and split under 20 ms;
  the age bound closes a group that never goes idle, losing nothing). The
  power-loss and fault suites run with the new grouping (section 5).

**Authorized but not built here (lever 3, study item 2):** folding the
directory records (one pending and one complete commit per batch since
OI-1003-Q143) into the output group's commit. It changes R-N102's commit
unit, so it needs `DirectoryRecords.tla` to model a directory record
committed with outputs before it is built. About 2 FULL commits (about
16 ms on the rig) per copy. **Update 2026-10-16:** the completion half is
built, modelled first (`GroupFinish`, `CompletionAfterChildren`); the
pending half cannot fold (`2026-10-16-s1-fold.md`).
