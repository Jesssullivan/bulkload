## What changed (first round; the immutable read described here was removed in the Q72 round)

- **Counter.** `source_wal_index_touched`
  (`Counter::SourceWalIndexTouched`) is the last entry of `Counter::ALL`.
  `Counters::render` writes the derived totals (`blake3_total_bytes`,
  `blake3_dest_bytes`, `sqlite_commits_total`, `full_flushes_total`) after
  `Counter::ALL`, so the new key lands before them and each of those four
  moves one field. Readers match keys by name. Its meaning changed in the
  review round below: it adds 1 for each WAL-aware snapshot that leaves a
  `-shm` beside its source, changed or not.
- **`provider_sqlite::snapshot`** is restructured around a private
  `Footprint`. It observes the source before the read, then `copy_source`
  runs the backup and closes the source connection. Last, `settle` counts
  the wal-index or re-checks a quiescent read. Counting happens whether
  the copy succeeded or refused.
- **Finding, and the fix it needed.** A WAL-aware read-only open of a
  WAL-mode database **with no `-wal`** also creates an empty `-wal`. This
  was measured with Python sqlite 3.51 and with the bundled 3.46 (mutant C
  below). That covers a checkpointed, closed database, and one whose writer
  has opened it but not read it yet. Such an `-wal` is a source write that
  Q36 does not cover, and P75 would be red on main's snapshot.
  - The fix: when the header says WAL (bytes 18 and 19 are 2) and there is
    no `-wal`, the main file holds the whole database. It is read with
    `immutable=1`: no lock and no sidecar.
  - A writer appending to the WAL does not touch the main file until a
    checkpoint. So `settle` refuses `SQLITE_STATE_CHANGED` unless the main
    file kept its identity and timestamps and no `-wal` appeared. The
    caller retries with a new output, as for any other refusal.
  - Residual: a writer that opens, writes, checkpoints and closes entirely
    within one read, inside one coarse timestamp tick of the main file's
    previous write, would go unseen. Listed under Open.
- **S2 instrument** (`crates/bulkload-bench/scripts/s2_budget.py`):
  - Each ON run records `source_wal_index_touched`, the sum over its
    counters lines, or None when no line reports the counter.
  - The verdict records `{total, runs_reported, runs_unreported}`, and the
    summary and the stderr `wal_index` line print it. RULINGS gains
    OI-1003-Q36.
  - Under `--evidence`, an ON run that does not report the counter is
    INCONCLUSIVE, so evidence always carries it.
  - The trace schema stays v1, because the field is additive.
  - Nothing was run on neo.
- **P75 SQLITE-SHM-EXCEPTION** is `crates/bulkload-agent/tests/sqlite_wal_index.rs`:
  - It runs 10 PINNED rows (5 shapes × 0 or 5 `-wal` frames) and 12
    fixed-seed cases.
  - The live writer is a child process (the test binary re-run), so its
    POSIX locks are its own.
  - A second test runs the `snapshot` verb and reads the counter from its
    counters line: 1 for `CrashedNoShm`, 0 for `CleanClosed`.
  - `source_wal_index_touched` per round is fixed by the shape: 1 for
    LiveWithShm, CrashedWithShm and CrashedNoShm, and 0 for LiveIdleNoShm
    and CleanClosed.
- **Docs:**
  - `docs/design.md`: the S2 list names both SQLite exceptions (Q16's lock
    and Q36's write), and the immutable read as pending a decision.
  - `docs/slo.md`: a dated 2026-10-06 bullet under the Q36 amendment, about
    the counter only. Earlier text is unchanged.
  - The property plan gains a P75 row after P35.

## Review round (2026-10-06, same lane and branch; history, superseded where it describes the immutable read)

A review of b1edf5b raised one high and five medium findings. All six were
judged valid and fixed.

- **Counter meaning (medium).** The first counter compared the `-shm`
  before and after the read. Beside a live writer the read usually leaves
  the bytes alone, so it reported 0 for a file it had opened read-write,
  mapped and locked.
  - Shown here: the new P75 oracle run against the old counter failed on the
    first pinned row, `LiveWithShm round 0: source_wal_index_touched (shm
    same)`, left 0, right 1.
  - Now `settle` adds 1 for every WAL-aware snapshot that leaves a `-shm`
    beside its source. So 0 means no snapshot opened a source wal-index.
  - It is an upper bound in two corners where SQLite never opens the `-shm`
    that is counted: a rollback-journal database with a stray `-shm`, and a
    snapshot refused before its first read of the source.
  - The snapshot no longer reads the `-shm` bytes. It only `lstat`s the
    sidecars. It still opens the main file to read its header.
- **P75 oracle (medium).** `check` now snapshots each source twice and
  asserts a value fixed by the shape, not the before/after comparison the
  implementation used. The second round pins the counter for a read that
  leaves the bytes alone. Each round prints `shm=created|changed|same|absent`.
  One CI-tier run printed, for LiveWithShm with 5 pending frames: round 0
  `1 shm=changed`, round 1 `1 shm=same`.
- **The quiescent re-check had no test (two medium findings).** Five unit
  tests in `provider_sqlite.rs` now cover it (the message of 9db8490 says
  six; five is right):
  - `settle` returns Ok for a still source;
  - it refuses `SQLITE_STATE_CHANGED` when a bare `-wal` appears, when a
    writer commits and stays open, when the main file is rewritten in place,
    replaced by a copy or removed, and when a writer commits, checkpoints
    and closes;
  - `snapshot_then`, a private seam that runs a closure between the read
    and `settle`, shows the whole snapshot refusing for both writer cases.
    `snapshot` passes a no-op.
  - The fixture sets the main file's mtime far in the past, so a later write
    moves it whatever the timestamp granularity.
- **Unratified immutable read (high).** The code stays, because the tests
  above and P75's strict reading depend on it, and it is marked everywhere

  - `docs/plans/2026-10-03-architecture-review.md` section 4 item 8 gains a
    dated note that points at it;

- **"Both bounded and counted" (medium).** `docs/design.md` now says only
  the wal-index write is counted, and that Q16's lock count is an open gap.
