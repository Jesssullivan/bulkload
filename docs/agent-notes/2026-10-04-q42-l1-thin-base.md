## The defect

The S3 estate evidence (`docs/evidence/s3-estate-sting-2026-10-04.md`,
findings 3 and 4) showed two costs:
- A linked worktree's head move re-packed 1.83 MB for a 3.5 KB change.
- Eight worktree items each carried their repository's 64 MiB blob, 546.7 MB
  in total.

The cause was the group-base writer, `write_with_prerequisites`. It ran
`git bundle create --all` with `^tip` lines. That marks only edge commits'
trees uninteresting, so the parentless staged and worktree snapshot
commits re-packed every tracked blob they share with HEAD. The chained
writer, `write_excluding_tip_trees`, already avoided that with
`rev-list --objects-edge-aggressive`. It then dropped the walk's `-<oid>`
edge lines, so pack-objects had no delta bases and a 64-byte edit to a
64 MiB blob packed the whole blob.

## What changed (`crates/bulkload-agent/src/git_carry/shared.rs`)

- `write_bundle` with a plan base now calls
  `write_excluding_tip_trees(private, bundle, &prerequisite_commits(private, base)?)`.
  Grouped and chained captures share one writer.
- That writer keeps the `-<oid>` edge lines on pack-objects' stdin.
  pack-objects reads each edge's tree as a preferred base. An edited blob
  then packs as a REF_DELTA against the copy the prerequisites hold, so the
  pack is thin. Restores complete it with `index-pack --fix-thin`: the
  import's `git fetch`, or `chain::flatten`'s. So does the next pass's
  blob-reuse fetch, which reads the bases from the source store (see the
  review round).
- `write_with_prerequisites` is deleted (about 75 lines), and
  `create_bundle` is folded into `write_full`, its only remaining caller.
- Snapshot commits stay parentless, so #172's pinned commit test keeps
  holding. `git_env::CONFIG`, `estate.rs` and `chain.rs` are untouched.

## Probes (git 2.54.0, the nix dev shell's)

The probe used a parentless snapshot commit over a tracked blob with a
64-byte overwrite, excluding a base tip that holds the original. Its
scripts were in scratch and are not durable; the numbers are the record.

| Writer | 4 MiB blob | 64 MiB blob |
|---|---:|---:|
| origin/main chained writer (edge lines dropped, no `--thin`) | 4,195,776 B | 67,129,535 B |
| edge lines kept and `--thin` | refused: `fatal: not a rev '-<oid>'` | refused |
| **edge lines kept, no `--thin` (this change)** | **373 B** | **2,514 B** |
| `pack-objects --revs --thin` (`S --not A`, git's own thin path) | 4,195,791 B | 67,129,550 B |

- **The dispatch said "passes --thin"; that does not work.** `--thin`
  makes pack-objects run its internal rev-list, which reads stdin as
  revisions and rejects edge lines. Edge lines on an object-list stdin make
  the pack thin by themselves. The writer omits `--thin`, and the code
  comment records why.
- git's own `--revs --thin` does not help either. It uses `--objects-edge`,
  not `-aggressive`, so the base tip of a parentless snapshot is not an
  edge.
- After `index-pack --fix-thin` in a repository holding only the base, the
  edited blob was a depth-1 delta (250 B, 167 B in the pack), and
  `fsck --connectivity-only` was clean.
- **`--all` already excludes HEAD's tree.** `--objects-edge-aggressive`
  marks the tree of every UNINTERESTING commit on the command line, and
  `--all` puts every private ref there, `refs/carry-export/head` included. A
  head move to an older commit therefore re-packs nothing. This is why the
  chained head-move row was already green on main.
- pack-objects keeps only the first `pack.window` (10) edges as preferred
  bases. The walk prints edge parents first, then uninteresting ref tips in
  ref order, and `refs/carry-export/head` sorts before every source ref.
  The P64 fixture has 12 orphan tips with blob-free trees to exercise this.

### pack.windowMemory=64m A/B (deliverable 6)

On the 64 MiB pair, the edge-kept pack is 2,514 B with
`pack.windowMemory=64m` and 2,514 B with it unlimited (0). pack-objects
took 2.33 s and 1.97 s; the whole probe's maxrss was 390,696 KiB and
408,436 KiB.
**64m does not block the delta.** pack-objects' window eviction keeps at
least one entry, and a preferred base sorts directly before its target
(same name hash, preferred base first). The estate-shaped runs below ran
under the hardened `git_env::CONFIG` (`pack.windowMemory=64m`) and also
delta'd the 64 MiB blob. No CONFIG change is needed; #172 owns CONFIG
anyway.

## P64 PACK-MINIMALITY and P65 THIN-DELTA

`crates/bulkload-agent/tests/git_group_minimality.rs` holds 18 table rows,
one `#[test]` each. The layouts are Grouped (main, a branch worktree and a
detached worktree: a 3-item group) and Chained (a group of one). The
mutations are first pass, head move, side commit, directory rename (the
pack.useSparse case), committed 64-byte edit, uncommitted 64-byte edit,
revert to older content, unchanged untracked payload and thin reuse (a
third pass). The large blob is 1 MiB + 17 B and incompressible, and
`rounds.bin` (64 KiB) is rewritten by every commit.

**The law, as restated in the review round (OI-1003-Q42 reading (a)).**
P64 is what the writer's walk guarantees, not the full closure of the
prerequisites:

```text
packed(B) ⊆ reach(refs(B))
packed(B) ∩ (C(B) ∪ under(T(B))) = ∅
```

`C(B)` is the commits the prerequisites reach. `T(B)` is the commits of
`C(B)` whose trees `--objects-edge-aggressive` marks: every prerequisite,
every ref of `B` whose commit is in `C(B)` (HEAD's), and every edge parent of
a packed commit. `under` is everything beneath those trees. Two costs stay
outside the law, and rows pin each:
- **Older content brought back** (`checkout <c1> -- rounds.bin`). The
  blob is in `reach(prerequisites)` but under no `T(B)` tree, so it is
  packed again whole: 69,248 B chained and 69,266 B grouped, against
  about 3.5 KB for the other pass-2 rows. Each row also reports the
  full-closure overlap `packed(B) ∩ reach(prerequisites(B))`. The revert
  rows pin it to exactly that blob, and every other row pins it empty.
- **Snapshot payload.** An unchanged 512 KiB untracked `payload.bin` is
  packed whole on pass 1 and again on pass 2: 528,228 B chained and
  528,249 B grouped on pass 2. #174 tracks it.

Each row:
1. Runs the verb binary for each pass (two passes; three for the thin-reuse rows).
2. Checks every item bundle of every pass against the law. Packed objects
   come from `index-pack --fix-thin` in a scratch store with the source as
   an alternate, keeping only offsets before the original trailer.
3. Asserts that no item bundle of a group, and no later-pass bundle, packs
   the base's large blob, and pins the full-closure overlap.
4. For P65, asserts that the edited blob is a delta under 1/64 of its size,
   and that its pack is thin (fix-thin appended its base).
5. Thin reuse: the third pass's retained capture is the thin pass-2 bundle.
   That pass must report no `reuse_unavailable` and
   `source_bytes_read` = the edited `notes.txt` alone. It must count
   `read_source_capture_reuse_bytes` ≥ the retained bundle plus the large
   blob (the base the fetch completed). Pass 2 and pass 3 must both be thin
   and declare prerequisites. Chained, both carry a `.prior` sidecar, so
   the apply flattens two thin links.
6. Runs `estate-apply` and compares every workspace: HEAD, `status
   --porcelain`, and every byte outside `.git`.

**Red on origin/main** (the build session's 12-row file against origin/main's
`shared.rs`): 8 failed, 4 passed. All six Grouped rows failed P64 at pass 1,
with the 1 MiB blob among the re-packed base objects. The chained committed

## Review round (2026-10-04, review fix session)

The lane review raised five medium findings; all five are fixed here.

1. **P64 overclaimed the full closure.** Reading (a) taken: P64 is restated
   as what `--objects-edge-aggressive` guarantees, in the test doc, the
   `write_excluding_tip_trees` comment and the `write_bundle` doc. Two
   revert rows pin the leftover: the reverted 64 KiB blob is packed whole,
   and it is the only full-closure overlap. Reading (b), filtering
   against the full closure, was not taken. It would walk the whole history
   of the prerequisites (every tree, from the source store) on every
   capture of every item. That read grows with history, not with the
   change, and git's own thin-pack negotiation makes the same edge-based
   trade. The operator may still rule (b).
2. **The reuse fetch's base read went uncounted** (and 4: R25). In
   `git_carry::retained_blobs`, the fetch now runs through `pack_child`,
   so its storage reads join `read_source_pack_readback_bytes`. The
   written pack's growth over the bundle's own pack (exactly the bases
   fix-thin appended) is added to `read_source_capture_reuse_bytes`.
   `shared::bundle_pack_len` is new and shares the header parser with
   `pack_object_count`. The `PackStats::bytes`, `counters.rs` and
   `docs/design.md` capture-counter text now says that
   `write_source_pack_bytes` bounds a thin capture's pack, not its reads.
   The table above replaces the reuse-read "saving".
3. **Snapshot payload is outside P64.** The test doc says so. Two
   untracked-payload rows pin the per-pass cost, and #174 is the
   follow-up.
4. See 2.
5. **No test covered reuse from a thin retained capture.** Two thin-reuse
   rows run a third pass (assertions under P64 above). Chained, the apply
   flattens two thin links.
