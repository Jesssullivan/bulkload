## The defect

The S3 estate evidence (`docs/evidence/s3-estate-sting-2026-10-04.md` on
`origin/feat/s3-estate-20261004`, findings 3 and 4) showed two costs:
- A linked worktree's head move re-packed 1.83 MB for a 3.5 KB change.
- Eight worktree items each carried their repository's 64 MiB blob, 546.7 MB
  in total.

The cause was the group-base writer, `write_with_prerequisites`. It ran
`git bundle create --all` with `^tip` lines. That marks only edge commits'
trees uninteresting, so the parentless staged and worktree snapshot
commits re-packed every tracked blob they share with HEAD. The chained
writer, `write_excluding_tip_trees`, already avoided that with
`rev-list --objects-edge-aggressive`. It then dropped the walk's `-<oid>`
edge lines, so pack-objects had no delta bases and a 64-byte edit to a
64 MiB blob packed the whole blob.

## What changed (`crates/bulkload-agent/src/git_carry/shared.rs`)

- `write_bundle` with a plan base now calls
  `write_excluding_tip_trees(private, bundle, &prerequisite_commits(private, base)?)`.
  Grouped and chained captures share one writer.
- That writer keeps the `-<oid>` edge lines on pack-objects' stdin.
  pack-objects reads each edge's tree as a preferred base. An edited blob
  then packs as a REF_DELTA against the copy the prerequisites hold, so the
  pack is thin. Restores complete it with `index-pack --fix-thin`: the
  import's `git fetch`, or `chain::flatten`'s.
- `write_with_prerequisites` is deleted (about 75 lines), and
  `create_bundle` is folded into `write_full`, its only remaining caller.
  The net change to `shared.rs` is +41/−107.
- Snapshot commits stay parentless, so #172's pinned commit test keeps
  holding. `git_env::CONFIG`, `estate.rs`, `git_carry.rs` and `chain.rs`
  are untouched.

## Probes (git 2.54.0, the nix dev shell's)

The probe used a parentless snapshot commit over a tracked blob with a
64-byte overwrite, excluding a base tip that holds the original. Its
scripts were in scratch and are not durable; the numbers are the record.

| Writer | 4 MiB blob | 64 MiB blob |
|---|---:|---:|
| origin/main chained writer (edge lines dropped, no `--thin`) | 4,195,776 B | 67,129,535 B |
| edge lines kept and `--thin` | refused: `fatal: not a rev '-<oid>'` | refused |
| **edge lines kept, no `--thin` (this change)** | **373 B** | **2,514 B** |
| `pack-objects --revs --thin` (`S --not A`, git's own thin path) | 4,195,791 B | 67,129,550 B |

- **The dispatch said "passes --thin"; that does not work.** `--thin`
  makes pack-objects run its internal rev-list, which reads stdin as
  revisions and rejects edge lines. Edge lines on an object-list stdin make
  the pack thin by themselves. The writer omits `--thin`, and the code
  comment records why.
- git's own `--revs --thin` does not help either. It uses `--objects-edge`,
  not `-aggressive`, so the base tip of a parentless snapshot is not an
  edge.
- After `index-pack --fix-thin` in a repository holding only the base, the
  edited blob was a depth-1 delta (250 B, 167 B in the pack), and
  `fsck --connectivity-only` was clean.
- **`--all` already excludes HEAD's tree.** `--objects-edge-aggressive`
  marks the tree of every UNINTERESTING commit on the command line, and
  `--all` puts every private ref there, `refs/carry-export/head` included. A
  head move to an older commit therefore re-packs nothing. This is why the
  chained head-move row was already green on main.
- pack-objects keeps only the first `pack.window` (10) edges as preferred
  bases. The walk prints edge parents first, then uninteresting ref tips in
  ref order, and `refs/carry-export/head` sorts before every source ref.
  The P64 fixture has 12 orphan tips with blob-free trees to exercise this.

### pack.windowMemory=64m A/B (deliverable 6)

On the 64 MiB pair, the edge-kept pack is 2,514 B with
`pack.windowMemory=64m` and 2,514 B with it unlimited (0). pack-objects
took 2.33 s and 1.97 s; the whole probe's maxrss was 390,696 KiB and
408,436 KiB.
**64m does not block the delta.** pack-objects' window eviction keeps at
least one entry, and a preferred base sorts directly before its target
(same name hash, preferred base first). The estate-shaped runs below ran
under the hardened `git_env::CONFIG` (`pack.windowMemory=64m`) and also
delta'd the 64 MiB blob. No CONFIG change is needed; #172 owns CONFIG
anyway.

## P64 PACK-MINIMALITY and P65 THIN-DELTA

`crates/bulkload-agent/tests/git_group_minimality.rs` holds 12 table rows,
one `#[test]` each. The layouts are Grouped (main, a branch worktree and a
detached worktree: a 3-item group) and Chained (a group of one). The
mutations are first pass, head move, side commit, directory rename (the
pack.useSparse case), committed 64-byte edit and uncommitted 64-byte edit,
on a 1 MiB + 17 B incompressible tracked blob. Each row:

1. Runs the verb binary: first pass, mutation, second pass.
2. Checks every item bundle of both passes against the law
   `packed(B) ⊆ reach(refs(B)) \ reach(prerequisites(B))`. Here `reach`
   is the full object closure. Packed objects come from `index-pack
   --fix-thin` in a scratch store with the source as an alternate, keeping
   only offsets before the original trailer.
3. Asserts that no item bundle of a group, and no second-pass bundle,
   packs the base's large blob.
4. For P65, asserts that the edited blob is a delta under 1/64 of its size,
   and that its pack is thin (fix-thin appended its base).
5. Runs `estate-apply` and compares every workspace: HEAD, `status
   --porcelain`, and every byte outside `.git`.

**Red on origin/main** (the final test file against origin/main's
`shared.rs`, binary otherwise identical): 8 failed, 4 passed. All six
Grouped rows fail P64 at pass 1: 9 of 23 to 25 packed objects are already
in the base, among them the 1 MiB blob. Chained committed and uncommitted
edits fail P65, packing the edited blob whole (1,048,895 B in the pack).
The four chained P64 rows pass on main, for the `--all` reason above.

**Green after:** 12 passed, 27 s with 4 test threads.

## Open

- **Ruling text.** OI-1003-Q42..Q46 are cited from the dispatch; their text
  is not in `docs/slo.md` on main (`3b634ba` records up to Q40).
- **design.md.** It does not yet say that capture bundles are thin packs
  completed with `index-pack --fix-thin` on import and flatten. This
  lane's file list did not include it, so a later docs pass should add
  one line.
- **Grouped items still never chain** (evidence finding "Grouped items
  never chain"). A grouped item's prerequisites stay the first pass's
  base, so each changed capture re-packs all history added since then,
  once per item. With this change that history is at least delta'd
  against the base. Making grouped items chain, or advancing the base, is
  a later lane's (estate.rs is out of scope here).
- **Reuse fetch of a thin retained bundle.** The next pass's blob-reuse
  fetch completes the thin pack in the private attempt directory, which
  appends the base (64 MiB here) and reads it from the source store. Net
  private growth still fell from 134.3 MB to 70.8 MB. Fetching only the
  worktree and filesystem rows without completing the pack would remove
  it; that touches git_carry.rs, which is out of scope here (evidence
  finding 5).
- **Ten preferred bases.** If more than nine edge parents precede
  `refs/carry-export/head` (ten or more new commits on distinct
  uninteresting parents in one pass), a worktree edit's large blob can
  miss its base and pack whole. That is correct, just larger. A writer
  could move HEAD's edge first; not done here, since nothing measured
  needs it.
- The self-audit grep for process-control words was not run; the
  pre-commit audit is authoritative (R-N92).
