**Counters asserted.** These are the per-run `TransferStats` fields
`source_bytes_read` and `bytes_received` (the S3 evidence's
`transferred_content_bytes`), plus the process counters of the measured run:
`read_source_file_bytes`, `read_hash_file_bytes` (the walk is metadata only)
and `transfer_racy_captures`. Measured runs hold one mutex per binary, so
the process deltas are exact. The walk leg asserts `bytes_read`,
`bytes_reread_on_resume`, `fresh_skipped`, `seats_seen` and `bytes_seen`,
plus every row's digest against `blake3(content)`.

**Seed policy.** Both files mirror `test_support::prop_config`, which is
`#[cfg(test)] pub(crate)` and out of an integration test's reach. They
always use `RngSeed::Fixed(CI_SEED)`. `BULKLOAD_PROPTEST_DEEP=1` runs 20
times the cases from the same seed. Neither file uses `RngSeed::Random` or
writes a failure-persistence file.

**Host load.** Only P19's recent-write case depends on the clock: its copy
must run inside the 2 s racy window of the seats it wrote. The racy seats
are written and copied under the binary's mutex. If that took over 1.5 s,
nothing is asserted and the case is rebuilt from scratch (8 attempts, then
it fails). Every other case settles first, so load cannot change its
verdict. The binary passed at load1 about 70.

**Wall time** (debug build, sting, load1 about 70). In the first green
`check-fast` run, `s3_transfer_resume` took 26.6 s and `s3_walk_resume`
0.7 s. After the review fixes (seven more delta or P23 cases, each with one
or two real 2 s settles) the transfer binary alone took 41 s and 54 s in two
runs. The
transfer binary's tests run in parallel. Each case settles the racy window
for real (about 2 s per settle), and `p23_…` is the longest test (about 32 s
when run alone on a busy host).

## Red on main: issues filed

- **#186.** A refused SQLite seat is re-read for its 16 sniff bytes on every
  run. Shrunk counterexample: one file of 5598 bytes plus one
  `SQLite format 3\0` seat, unchanged rerun, `source_bytes_read=16` (bound
  0). This breaks file inequality 1 and the unchanged clause, as the audit
  expected.
- **#187.** A changed source file is refused `GIT_DESTINATION_OCCUPIED` on
  the rerun instead of being superseded (WP0(d) is not implemented).
  Counterexample: `f0` +1 byte and `f1` +60229 bytes after a first pass.
  Inequality 1 holds (`source_bytes_read=373043` = the changed and added
  bytes). Both seats are refused, and `bytes_received=13994` is spent on
  them. Inequality 2 and convergence fail, as the audit expected (blocked by
  WP0(d)). Side note on the issue: the code is a Git one, on an
  ordinary-file transfer.

## Review round (2026-10-06): two medium findings fixed

Only `tests/s3_transfer_resume.rs`, the plan rows P21 and P23, and this note
changed. No production code.

1. **Inequality 2 never reached chunk sharing in the CI corpus.** Before the
   fix M6 left `p21_added_seats_…` green. Now:
   - `delta_case(.., sharing = true)` draws carried file 0 at 196608..=393216
     bytes (several CDC chunks) and makes the first added seat a
     `CopyOf` or the new `SliceOf` of it, with a tail of 0 or 1..70000
     bytes. The other added seats are free and may copy any file again.
   - The property keeps a case only if the model's absent bound is strictly
     below the added size (`prop_assume!(shares_a_chunk(..))`).
   - The absent chunks are de-duplicated by digest across the run
     (`DeltaModel::absent_bytes`).
   - The six CI cases, as (absent, added) bytes: (352770, 660756),
     (525025, 610696), (0, 285176), (1, 310055), (340957, 536831),
     (213224, 470820). `bytes_received` equalled the absent bound in all six.
   - M6 rerun in a scratch copy: the property is red (table above).
2. **No green test had a refused seat.** `Sniff::EveryRun` states what main
   does: each run after the first reads exactly 16 bytes per refused seat on
   top of the expected reads. Under it the full P23 and P21 bodies run green
   with 1–2 SQLite seats: the fixture's refusal set on every run, the same
   applied/reused/completed counts, convergence, a rerun that receives 0, and
   `source_bytes_read` exact to the byte. These tests state the #186
   residue, not the contract. When #186 is fixed they go red: delete them and
   remove `#[ignore]` from the `Sniff::Once` properties.

**Found while fixing 1 (not in the review).** Two seats added in one run
that carry the same absent chunk: main sends it once or twice, depending on
whether the first twin is staged before the second is planned. The pinned
twin row (two 200000-byte seats with the same bytes) received 555000 bytes
in one run and 355000 in another, against a de-duplicated bound of 355000.
So the strict once-per-run reading of inequality 2 is unstable on main. The
per-file reading (each seat's distinct absent chunks, which is what the S3
evidence harness computes) always held. The green properties assert the
de-duplicated bound plus `twin_bytes` (0 unless a case has twins, and 0 in
every CI case); the strict reading is the ignored
`p21_pinned_twin_seats_cross_their_shared_chunks_once`. No issue was filed:
which reading is the contract needs a ruling first.

**Also observed.** An interior `SliceOf` shares little: with normalised
chunking, a cut point of the holder is often not a cut point of a slice that
starts mid-chunk. Slices in the CI cases shared 0 to about 86 KB. Whole
copies and prefix slices share all but the last chunk.

## Open

- **P19 tick boundary and git half.** The i128 (stamp, clock) triples
  around the boundary, and the git `racy`/`reuse_at` predicate, need a hook.
  `transfer::capture_clock`/`set_capture_clock` are `#[cfg(test)]` and
  `git_carry::racy` is `pub(crate)`, so an integration test cannot pin the
  clock. A public pure predicate, or a test-support feature, would let P19
  run on the exact boundary instead of only the real clock.
- **P23 retention budgets.** These are not drawn, because `RETAIN_OVERRIDE`
  is `#[cfg(test)]` (same hook question).
- **P18 store-level half** (commit_outputs sequences and reopen) is still
  open (plan PR4).
- **Seed mirror vs the plan.** The plan's deep tier says random seeds
  locally. These files keep the seed fixed in both tiers, per the task (no
  `RngSeed::Random`). The no-fuzz-seed-guard lane should confirm that this is
  the policy it enforces.
- **`SqliteCache::record_digest` does not `record` the stat identity**,
  unlike the trait default and `MemoryCache`. A stat-only walk after a
  hashed one therefore reports fewer `fresh_skipped` on the SQLite cache. P21
  does not assert `fresh_skipped` for stat-only walks. Whether that
  asymmetry is intended is unknown.
- **The unchanged-estate ≤ 10 % wall-clock clause** is not asserted here,
  because wall time is informational under OI-1003-Q35. Git `census_walks`
  is outside these file-transfer properties.
- When #186 and #187 are fixed, remove the `#[ignore]` on the three red
  properties. Their assertions are the full statements. When #186 is fixed,
  also delete the three `…issue_186_residue…` tests.
- **Reading of inequality 2 for twins in one run** (above): needs a ruling,
  then an issue if the strict reading is the contract.
- **A failing sharing property shrinks slowly.** Under M6 the shrink replayed
  the failing case about 25 times (146 s for the P21 tests). It only costs
  time when the property is already red.
- **Low review findings, not fixed in this round** (as instructed): the thin
  P23 cut dimension (k = 0 never drawn or pinned); P18 holders only
  overwritten whole and not settled; P19 never makes an already-committed
  seat racy, and its `Recent` case fails after 8 overruns on a slow host; the
  deep tier keeps a fixed seed, unlike `test_support::prop_config` and plan
  section 3; the wall-time floor from real settles (deep tier 728 s); the
  ignored P23 refused-seat test fails at the resume clause, before the
  rerun clause its name describes, and a cut session asserts read-once only
  in aggregate.
