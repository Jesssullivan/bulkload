**Counters asserted.** These are the per-run `TransferStats` fields
`source_bytes_read` and `bytes_received` (the S3 evidence's
`transferred_content_bytes`), plus the process counters of the measured run:
`read_source_file_bytes`, `read_hash_file_bytes` (the walk is metadata only)
and `transfer_racy_captures`. Measured runs hold one mutex per binary, so
the process deltas are exact. The walk leg asserts `bytes_read`,
`bytes_reread_on_resume`, `fresh_skipped`, `seats_seen` and `bytes_seen`,
plus every row's digest against `blake3(content)`.

**Seed policy.** Both files mirror `test_support::prop_config`, which is
`#[cfg(test)] pub(crate)` and out of an integration test's reach. They
always use `RngSeed::Fixed(CI_SEED)`. `BULKLOAD_PROPTEST_DEEP=1` runs 20
times the cases from the same seed. Neither file uses `RngSeed::Random` or
writes a failure-persistence file.

**Host load.** Only P19's recent-write case depends on the clock: its copy
must run inside the 2 s racy window of the seats it wrote. The racy seats
are written and copied under the binary's mutex. If that took over 1.5 s,
nothing is asserted and the case is rebuilt from scratch (8 attempts, then
it fails). Every other case settles first, so load cannot change its
verdict. The binary passed at load1 about 70.

**Wall time** (debug build, sting, load1 about 70). In the green `check-fast`
run, `s3_transfer_resume` took 26.6 s and `s3_walk_resume` 0.7 s. The
transfer binary's tests run in parallel. Each case settles the racy window
for real (about 2 s per settle), and `p23_…` is the longest test (about 32 s
when run alone on a busy host).

## Red on main: issues filed

- **#186.** A refused SQLite seat is re-read for its 16 sniff bytes on every
  run. Shrunk counterexample: one file of 5598 bytes plus one
  `SQLite format 3\0` seat, unchanged rerun, `source_bytes_read=16` (bound
  0). This breaks file inequality 1 and the unchanged clause, as the audit
  expected.
- **#187.** A changed source file is refused `GIT_DESTINATION_OCCUPIED` on
  the rerun instead of being superseded (WP0(d) is not implemented).
  Counterexample: `f0` +1 byte and `f1` +60229 bytes after a first pass.
  Inequality 1 holds (`source_bytes_read=373043` = the changed and added
  bytes). Both seats are refused, and `bytes_received=13994` is spent on
  them. Inequality 2 and convergence fail, as the audit expected (blocked by
  WP0(d)). Side note on the issue: the code is a Git one, on an
  ordinary-file transfer.

## Open

- **P19 tick boundary and git half.** The i128 (stamp, clock) triples
  around the boundary, and the git `racy`/`reuse_at` predicate, need a hook.
  `transfer::capture_clock`/`set_capture_clock` are `#[cfg(test)]` and
  `git_carry::racy` is `pub(crate)`, so an integration test cannot pin the
  clock. A public pure predicate, or a test-support feature, would let P19
  run on the exact boundary instead of only the real clock.
- **P23 retention budgets.** These are not drawn, because `RETAIN_OVERRIDE`
  is `#[cfg(test)]` (same hook question).
- **P18 store-level half** (commit_outputs sequences and reopen) is still
  open (plan PR4).
- **Seed mirror vs the plan.** The plan's deep tier says random seeds
  locally. These files keep the seed fixed in both tiers, per the task (no
  `RngSeed::Random`). The no-fuzz-seed-guard lane should confirm that this is
  the policy it enforces.
- **`SqliteCache::record_digest` does not `record` the stat identity**,
  unlike the trait default and `MemoryCache`. A stat-only walk after a
  hashed one therefore reports fewer `fresh_skipped` on the SQLite cache. P21
  does not assert `fresh_skipped` for stat-only walks. Whether that
  asymmetry is intended is unknown.
- **The unchanged-estate ≤ 10 % wall-clock clause** is not asserted here,
  because wall time is informational under OI-1003-Q35. Git `census_walks`
  is outside these file-transfer properties.
- When #186 and #187 are fixed, remove the `#[ignore]` on the three red
  properties. Their assertions are the full statements.
