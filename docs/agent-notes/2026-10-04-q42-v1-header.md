## Round 2: the #178 review findings (`9e7692c`)

Four medium/high findings, all judged valid and fixed in one signed
commit. The code was drafted by an earlier attempt of this round that
ended before committing; this session reviewed every hunk, re-ran the
checks, and committed it.

1. **Old readers could not detect the new format (medium).** The table
   ref was `refs/carry-export/ref-table-v1`, inside the prefix every
   pre-table reader imports, so main `818926a` imported a new capture's
   `ref-tip-v1/<oid>` refs as if they were the source's and reported
   success. Reproduced on sting with the `818926a` binary and a capture
   from round 1's head: `git-import` and `git-restore` both succeeded,
   leaving `.../ref-table-v1` and two `.../ref-tip-v1/<oid>` refs and none
   of the source's `refs/heads/*` or `refs/tags/*`. **Fix:** the table ref
   is `refs/carry-ref-table/v1`, outside the prefix, and is the format's
   marker. Every pre-table reader (`import_verified`, `shallow::unpack`, a
   plan base's `prerequisite_commits`) refuses a name outside
   `refs/carry-export/` `GIT_INVENTORY_MALFORMED` before it writes a ref.
   New readers accept it through `ref_table::carried_name`. After the fix,
   the same `818926a` binary refused a capture from this tree
   `GIT_INVENTORY_MALFORMED` for both `git-import` and `git-restore`; this
   tree's binary imported it exactly (`refs/heads/main`, `refs/heads/side`,
   `refs/tags/v1` under the import namespace). Test
   `a_reader_before_the_table_refuses_a_new_format_capture`: the frozen
   pre-table header rule refuses self-contained, plan-base, chained-link
   and shallow (inner inventory) new-format captures, and still reads the
   old binary's 23-ref capture. `docs/design.md` and the design note's
   Open section record the no-mixed-version rule.
2. **The import fetch was still quadratic (high).** One exact refspec per
   distinct object costs O(D x advertised) (the reviewer measured 56 s,
   232 s and 1,001 s of CPU at 10k, 20k and 40k tips, git 2.52).
   **Fix:** `unbundle_objects` replaces `fetch_advertised`: `git bundle
   unbundle` (index-pack, `--fix-thin` for a thin bundle; writes no ref),
   then one `rev-list --objects --quiet --stdin --not --all` walk over the
   distinct values with `^<prerequisite>` lines, git's own
   `check_connected` shape. A first walk that succeeds means the
   destination holds every closure already, and nothing is unbundled, as
   `fetch` did. No ref name is matched.
3. **Thin headers are 165 B per distinct object (medium).** A prerequisite
   line (54 B; 78 B SHA-256) per source-held commit on top of the 111 B
   tip line, so the thin cap falls at about **101,680** distinct objects
   (SHA-1) and **70,790** (SHA-256), not 151,100 and 105,500 (those are the
   self-contained bounds). `write_chained` refused `OVER_CAP` with no
   fallback, so the item stranded: every later pass is offered the same
   chain, which never grows to its depth reset. **Fix:**
   `write_excluding_tip_trees` measures the thin header and, over the cap,
   writes self-contained through `write_full` and returns `chained ==
   false`; the plan-base path (`write_bundle`) takes the same fallback.
   Apply already decides thin-ness from the bundle's own prerequisites
   (`requires_base`), and `publish_prior` records no prior for a
   self-contained pass. Only a self-contained header over the cap still
   refuses. Tests: `a_chained_pass_over_the_thin_cap_is_written_self_contained`
   (cap lowered to one byte under the pass's thin header: self-contained,
   imports exactly; at its own length it stays thin), and
   `writers_measure_an_over_cap_header_before_writing_it` (320,000 fake
   prerequisites fall back; with 170,000 private refs the fallback itself
   refuses, nothing left behind).
4. **No test ran the distinct-heavy regime (medium).**
   `tests/refs_scale_distinct.rs` (new integration test): every ref at its
   own commit. The CI row (mandatory tier) runs 32,768 refs: the header
   law (`<= 2048 + 111 B x D`, chained `<= 2048 + 165 B x D`), exact
   import of both passes, and the agent's own `git-import` CPU (reaped
   with `wait4`, so its git children count and concurrent tests do not)
   under `20 s + 2.5 ms x D`. The quadratic fetch would cost about 670 s
   at this size against a 102 s budget. The deep row
   (`BULKLOAD_PROPTEST_DEEP=1`, local) runs 110,000 distinct commits,
   where the chained pass's thin header (about 18.2 MB) is over the cap
   and falls back self-contained. The design note restates every claim
   per distinct object, not per ref.

## Round 3: recheck and ship (verdict CLEAN, PR #182)

This stage checked every medium/high finding adversarially against
`origin/feat/q42-v1-header-20261005` at `1343757`. It read the whole
diff since the build head `03a6e59`, and changed no code.

1. **The import is linear (high): fixed.** `unbundle_objects` checks each
   header line's oid and name (`carried_name`) before taking any object.
   The connectivity walk is the same as git's `check_connected`:
   `--stdin` lines are read with their own flags, then `--not --all`.
   rev-list's `finish_object` refuses a missing blob, so the walk proves
   every closure. The global config is `/dev/null` (`git_env::SET`), so
   dropping `fetch` loses no `transfer.fsckObjects` behaviour.
   `chain::flatten` uses glob refspecs, which are linear, and it carries
   the relocated table ref. The other import steps are linear: `expand`,
   the names loop and one update-ref transaction. The deep row's CPU
   agrees: 3.4x the objects cost 3.5x the CPU.
2. **Older readers refuse (medium): fixed.** `818926a`'s
   `import_verified` refuses every header name outside
   `refs/carry-export/` before its `fetch` and before any ref write. Its
   restore callers reach it before laying down any ref:
   - in-place apply writes only its receipt directory first;
   - `restore_staged` only creates and `git init`s the destination;
   - `restore_linked_staged` calls the import first.

   Both side effects are the same for any malformed bundle. The relocated
   ref reaches every header: `refs()` lists all refs, `bundle create
   --all` is used, the shallow inner inventory is `refs()`, and
   `prerequisite_commits` skips the table before its prefix check. A header
   from the unshipped round-1 format (tips with no
   `refs/carry-ref-table/v1`) is refused by `expand`, not mis-imported.
3. **Thin-cap fallback (medium): fixed.** The arithmetic holds:
   - 111 + 54 = 165 B per distinct object, and 159 + 78 = 237 B on SHA-256;
   - 16 MiB / 165 = 101,680 and 16 MiB / 237 = 70,790;
   - self-contained, 16 MiB / 111 = 151,146 and 16 MiB / 159 = 105,517.

   The consumers handle a self-contained fallback:
   - `publish_prior` writes no link when `chained` is false;
   - `import_base`, `retained_capture` and `chainable`, and every `.base`
     reader, are gated on `requires_base`. A fallen-back plan-base item
     keeps an unused `.base` sidecar, which is harmless.
4. **The distinct-heavy regime is tested (medium): fixed.** The CI row
   (32,768) is in the mandatory tier, and its CPU budget separates linear
   from quadratic (about 102 s against about 670 s). The deep row is
   local. The design note states its claims per distinct object.

No new medium or high defect was found. The seven low findings stay as

come before `bundle unbundle`, and only `canonical_tail` and the table

## Open

- **Operator ruling: the persisted format, with no mixed-version
  apply.** Every new v1 capture is written with a ref table; captures
  written before still restore (tests above). A capture with a table is
  applied only by a build that reads one: a destination, and any build
  pinned to restore a retained corpus later, must run this format's build
  or newer; an older one refuses it `GIT_INVENTORY_MALFORMED` (never a
  wrong ref set). Ratify, or rule a threshold (old format below N refs).
- **All-distinct inventories.** The header is 111 B per distinct object
  self-contained (159 B SHA-256) and 165 B thin (237 B SHA-256). A thin
  header over the cap now falls back self-contained; a self-contained
  header over the cap (about 151,100 distinct objects, 105,500 SHA-256)
  is still refused typed. Anchoring commit tips under octopus anchor
  commits would make it O(1), but `source_held_tips` would then need the
  prior's pack, not its header.
- **Smaller table** (about 1.3 MB per chained pass at 119,761 refs): object
  indexes into the tip list instead of object names.
- **Old-format apply at 119,761 refs cost 284 s of CPU** in round 1
  (flatten's loose refs, and fetch matching 1,032 refspecs against 119,768
  advertised refs). Round 2 removed the fetch term; the remainder was not
  re-measured.
- **Low review findings, not fixed (dispatch):** header name validation
  now runs after the objects are taken; the shallow envelope's precheck is
  approximate and leaves its pack on refusal; the REFS-SCALE rows (now
  also the 32,768 distinct row) run in the mandatory tier and write
  hundreds of MB of loose refs under the temp dir; `q42_probes.py` still
  models one header line per ref; the fixed row's test docs say 131,072
  refs over about 1,200 distinct where the run is 138,416 over 726, and
  symref and linked-worktree "exactness" is as described above; the round
  1 CPU rows are single ungated samples; each changed capture repacks the
  whole table and adds two to four git children.
- **Pre-existing, not fixed here:** `estate-apply` of a refs-imported item
  whose repository does not exist refuses `GIT_INVENTORY_MALFORMED`
  (`verify_bundle` masks `git -C`'s failure); and `chain::flatten` with a
  relative corpus path resolves its scratch paths twice under `git -C` and
  refuses `GIT_INVENTORY_MALFORMED`. Both seen while measuring; candidates
  for issues.
